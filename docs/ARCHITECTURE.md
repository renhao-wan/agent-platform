# 架构文档 — 企业内部统一 AI 助手平台

> 一句话：**员工打一句话，AI 就去真实地操作公司内部的业务系统。**
> 业务系统零改造接入（交一份 OpenAPI 接口文档即可），模型由平台统一供给，敏感操作人工确认。

---

## 1. 系统定位

**解决什么问题**：企业内部每个业务系统（预订、报修、审批……）想加上 AI 能力，各自对接一遍大模型——重复建设、成本分散、无法治理。

**方案**：建一个**统一的 AI 助手平台**，把"AI 怎么用工具"这件事收敛到一处：

- 对**业务系统**：零改造。提供 OpenAPI 文档，接口自动注册为 AI 可调用的工具；
- 对**员工**：一个入口。自然语言跨系统办事，过程全程可见；
- 对**平台**：模型统一供给、用量统一管控、危险操作统一拦截。

**不是什么**：不是智能客服（客服回答问题，本系统执行操作——产出是真实的数据库变更，不是一段话）；不跨企业边界（接入方须为本公司内部系统，员工走统一身份）。

## 2. 总体架构

```
                    ┌───────────────────────────┐
                    │       用户（企业员工）        │
                    └─────────────┬─────────────┘
                                  │ 浏览器 · 一句话
                                  ▼
┌────────────────────────────────────────────────────────────────┐
│                    agent-platform（:8000）                       │
│                                                                │
│  ① 用户接入层【已实现】                                            │
│     员工登录(JWT) → 角色随会话带到工具层，在调用点强制校验                │
│                    │                                           │
│  ② Agent 运行时【已实现】                                         │
│     ReAct 显式循环：规划 → 工具调用 → 观察 → 反思 → 回答             │
│     SSE 分阶段直播 · 上下文裁剪 · Token 打点 · 敏感操作挂起等确认     │
│     内部工具本地执行：recallHistory（会话记忆）· search_knowledge（RAG）│
│                    │ ToolGateway（进程内方法调用）                  │
│  ③ 工具层【已实现】                                               │
│     OpenAPI → Tool 自动注册                                       │
│     闸门1 清单组装 · 闸门2 执行点鉴权 · 泛化 HTTP 转发               │
└─────────┬──────────────────┬──────────────────┬─────────────────┘
          ▼                  ▼                  ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
   │ 会议室预订系统 │    │  报销系统     │    │  报修系统     │
   │ （已接入·真实）│    │（已接入·模拟） │    │（已接入·模拟） │
   └─────────────┘    └─────────────┘    └─────────────┘
   ↑ 业务系统零改造：不碰模型、不写 AI 代码，只需提供接口文档（并可用扩展字段声明角色要求）

   模型：平台统一供给（OpenAI 兼容协议，yml 配置可换供应商）→ 只有 ② 用它
   Embedding：SiliconFlow bge-m3（与 chat 模型分离，因为聊天供应商没有 embeddings 接口）
   基础设施：MySQL（工具注册/会话/用量打点） + Postgres + pgvector（知识向量）
```

三个系统都在 `/v3/api-docs` 暴露契约，平台启动时逐个拉取注册（`platform.gateway.sources`）——**"契约可访问"就等于"工具可用"**。两个模拟系统用 WireMock 实现，只写 mappings + 一份 OpenAPI，不写业务代码：它们的职责是提供"同一用户在不同系统权限不同"这件事的对照面（闸门 2 只有跨系统才有说服力），以及**失败语义的对照面**——它们和真实单体一样用标准状态码表达失败（缺身份 401 / 他人数据 403 / 目标不存在 404 / 状态不允许 409），而不是对任何输入都回 200。

**分层职责**：

| 层 | 职责 | 关键点 |
|---|---|---|
| ① 用户接入层 | 认识"你是谁"，把角色带到执行点 | JWT + 角色；`/admin/**` 额外要求 ADMIN；**不在这一层裁剪工具** |
| ② Agent 运行时 | 决定"怎么做"：选工具、造参数、看结果、定下一步 | 显式 ReAct 循环，每步可插桩（事件/确认/上限） |
| ③ 工具层 | 决定"怎么安全地做"：清单组装、执行点鉴权、转发 | 与 ② 同进程，`ToolGateway` 一次方法调用即达 |
| 业务系统 | 只提供接口（OpenAPI 文档） | 对 AI 零感知 |

## 3. 一次完整请求（业务流程）

用户输入："**帮我订下周三下午两点、能坐 8 人的会议室**"

```
用户                ② Agent 运行时           ③ 工具层            会议室预订
 │                        │                     │                     │
 │──"帮我订下周三…"──────▶│                     │                     │
 │                        │ 0. LLM 读工具清单      │                     │
 │◀─ plan(模型决策) ──────│                     │                     │
 │                        │ 1. listTools ──────▶│ 下发全部工具+角色声明   │
 │                        │◀── 工具清单 ─────────│                     │
 │                        │                     │                     │
 │                        │ 2. LLM 决策：先查房间（参数自填：              │
 │                        │    date=2026-10-07 由"下周三"换算而来）        │
 │◀─ plan/tool_call ──────│                     │                     │
 │                        │ 3. callTool ───────▶│ 4. 闸门2 + 转发 ─────▶│ 查库
 │                        │◀── 真实结果 ─────────│◀────────────────────│
 │◀─ tool_result ─────────│                     │                     │
 │                        │ 5. LLM 观察→反思：    │                     │
 │                        │    房间唯一满足→直接订 │                     │
 │                        │ 6. callTool(create) ────────────────────▶│ 写库
 │                        │                     │◀── 预订号 9 ─────────│
 │◀─ answer ──────────────│ "已订好 B401，预订号9" │                     │
 │◀─ done ────────────────│                     │                     │
```

注：`listTools` / `callTool` 是 `ToolGateway` 的进程内方法调用，不是网络往返——上图把它们画成一次"调用"只为标出职责边界。

**敏感操作分支（取消类工具 `require_confirm=true`）**：第 6 步前循环挂起 → 推 `confirm_request` 事件 → 用户点"同意/拒绝" → 恢复执行或把"用户拒绝"作为观察喂回模型。

**知识检索分支（平台内部工具）**：问题涉及制度、流程、标准时，模型调用 `search_knowledge`。它与 `recallHistory` 同构——不进工具层、不过闸门 2，由 `AgentRunner` 本地执行：query 向量化 → pgvector 相似度检索（角色过滤写进 SQL，无权内容不进候选集）→ 命中块作为观察回填。检索失败同样只返回文本观察，不打断循环（[KNOWLEDGE-RAG.md](KNOWLEDGE-RAG.md)）。

**错误自愈（实测）**：模型首次 `create` 时间格式错（`14:00:00`）→ 业务系统返回 400 → 模型自动改为 `14:00` 重试成功——工具失败包装为 `isError=true` 的文本观察交模型决策，不打断循环。

**前提是业务系统真的用非 2xx 表达失败**：`GenericHttpForwarder` 只以"非 2xx 或异常"判定 `isError`。业务系统若把业务异常也装在 HTTP 200 的响应体里（`{"code":1001,"message":"预订不存在"}`），平台拿到的就是一句正常的观察，模型于是把"该时段已被占用"读成"订好了"。业务码是给人排查用的，**状态码才是调用方判断成败的依据**；接口文档里要写明失败用哪些状态码。唯一例外是幂等重放——它返回的是既有记录，语义上属于成功，保持 2xx。

## 4. 用户权限：核心原则与三道闸门

### 4.1 核心原则

**模型只提议、不授权；权限校验在代码里，不在模型脑里。**
AI 的工具选择是一个"建议"，真正的安全边界在工具层执行点——由不经过模型的代码，按会话绑定的真实用户身份强制校验。因此模型幻觉出工具名、或被提示注入（"你现在是管理员"）都无法越权：校验看的不是模型说了什么，而是用户是谁。

### 4.2 三道闸门

```
AI（提议者）："我想调 admin_delete_user"
      ↓
【闸门1·清单组装】listForModel 下发该网关全部启用工具，不按角色裁剪
   → 角色要求写进工具描述，模型知道"这个能力存在、但当前身份可能不够"
   → 为什么不裁掉：裁掉的话模型只会答"我没有这个功能"，把权限问题说成能力问题
      ↓
【闸门2·执行点强制鉴权】★ 安全边界 ★
   invoke 到达工具层 → 校验 会话用户角色 × tool.required_role
   → 不匹配：包装为 isError=true 的结果拒绝（模型读后转述用户，循环不中断）
      ↓
【闸门3·敏感操作人工确认】
   有权调用的破坏性/不可逆操作 → confirm_request 挂起 → 用户点同意才执行
```

模型对"能不能调"的抉择因此分三段：**提前判断**（描述里已披露角色要求）→ **尝试**（照常发起调用）→ **被拒后转述**（闸门 2 返回 `权限不足：需要 X 角色`，模型据此向用户说明，而不是把失败说成自己不会）。

### 4.3 现状：三道闸门均已实现

- **接入鉴权**：用户 JWT 一套打天下——`/api/v1/chat`、`/api/v1/confirm` 校验 Bearer token，`/admin/**` 额外要求 `ADMIN` 角色（403 输出"需要 ADMIN 角色"）。没有第二套凭证体系。
- **闸门 1 / 闸门 2**：都在 `gateway/registry/ToolAccessService`，被 `InProcessToolGateway` 调用，即 `AgentRunner` 调工具时的必经之路。
- **闸门 3**：`ConfirmManager` 挂起 + `POST /api/v1/confirm` 恢复（同意/拒绝/超时三态均已实测）。
- **角色要求从哪来**：业务系统在自己的 OpenAPI 里用扩展字段声明（`x-required-role` / `x-require-confirm`），平台导入时读取。平台不猜测接口语义——"哪个接口要管理员"是业务系统的契约，不是平台的业务知识。
- **业务调用身份**：转发时按来源附服务级凭证 `X-Service-Key`，并带上 `X-On-Behalf-Of-User: {uid}` 声明"代表哪个最终用户"，业务系统据此把数据记在本人名下（仅在服务凭证校验通过时才采信该头）。

### 4.4 闸门 2 的核心实现

模型可能幻觉出不存在的工具名，也可能被提示注入诱导去调越权工具，因此执行前必须再校验一次。拒绝**包装为 `isError=true` 的文本结果**而非异常——模型读得到、循环不断：

```java
// ToolAccessService.invoke：定位工具后、转发之前
String requiredRole = tool.get().getRequiredRole();
if (requiredRole != null && !requiredRole.equals(userRole)) {
    return new ToolCallResult(true, "权限不足：需要 " + requiredRole + " 角色");
}
```

两道闸门的共同约定：**失败永不抛异常**，一律返回文本观察（`ToolCallResult.isError`）——这是 ReAct 循环能"看到失败并自己决定下一步"的前提。

### 4.5 一次越权尝试的完整流转

```
普通员工："帮我把 3 号预订取消"（cancel 要求 ADMIN）
 ① 模型在清单里看得到 cancel，描述里标着"需要 ADMIN 角色"
 ② 模型仍发起调用（或幻觉/被注入硬调）
 ③ ToolAccessService.invoke：role=STAFF ≠ ADMIN → isError=true 拒绝
 ④ 模型读到"权限不足" → 转述用户"这个操作需要管理员权限"
 ⑤ （若为管理员：走已有的 confirm_request 人工确认闸门）
```

### 4.6 AI 出错的分类对策（均已实现）

| 错误类型 | 机制 | 代码位置 | 状态 |
|---|---|---|---|
| 参数/格式错 | 错误回喂自纠 | `ToolAccessService.invoke` isError 包装 + 系统提示词 | ✅ 实测（400 时间格式 → 自改重试成功） |
| 死循环 | 步数熔断 | `LoopGuard`（maxSteps=8） | ✅ |
| 有权但危险 | 人工确认闸 | `require_confirm` 列 + `ConfirmManager` 挂起 | ✅ 实测三态 |
| 重复写入 | 语义幂等键 | booking SHA-256(userId\|roomId\|date\|…) | ✅ 实测 |
| 越权调用 | 闸门 2 执行点鉴权 | `ToolAccessService.invoke` | ✅ |

> 设计原则：**接入零成本，授权有边界**。技术上接一个新系统只需导入 OpenAPI；治理上必须回答"谁能用、以谁的身份、留什么痕"。

## 5. 模型策略

- 模型**只被 Agent 运行时使用**（工具层、业务系统均不依赖 LLM）；
- 平台统一供给：OpenAI 兼容协议，`yml` 配置供应商（默认 DeepSeek，`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` 三个环境变量一改即切厂商）；
- Embedding 独立配置（默认 SiliconFlow `BAAI/bge-m3`）：聊天供应商不提供 embeddings 接口，两者不能共用同一组凭证；未配置 key 时知识库整体不装配；外部调用带 3s/20s 超时与指数退避重试（仅可恢复错误），用量按模型计入 `knowledge_usage`；
- 演进路径：单模型（现状）→ 模型配置入库热切换 → 按接入方/场景路由不同模型（触发条件：成本分摊或需求分化）。

## 6. 关键设计决策（详见 docs/adr/）

| 决策 | 一句话理由 |
|---|---|
| 滑窗 + 摘要混合裁剪（ADR-003） | 纯滑窗丢关键事实、纯摘要成本翻倍；实测总 Token 降 31.8%，代价 +48.8% 重查次数 |
| 工具前置路由接口先行、默认休眠（ADR-004） | 工具数未达阈值时整链休眠、全量直通——规模化前零开销，规模化后自动武装 |
| 会话记忆用内部工具调回而非 RAG（ADR-005） | 对话消息短碎、上下文依赖强，嵌入质量天然差；把 RAG 推迟到规模证明它必要的时刻 |
| 进程内工具调用，删除 MCP 协议层与自环（ADR-006） | 自环理由只有"预留拆分部署"且从未兑现，代价是每次调用多一跳网络、异常跨协议层 |
| 权限要求与工具来源从业务契约读取（ADR-007） | 角色/敏感度由业务方声明、契约启动时自动拉取——平台不编码业务语义，接入方零改平台 |
| 知识库 RAG 与会话记忆分治（KNOWLEDGE-RAG.md） | 对话历史短碎、上下文依赖强，语义检索收益低；制度文档长且有结构，适合按标题切块 + 向量检索 |
