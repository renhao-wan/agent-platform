# 架构文档 — 企业内部统一 AI 助手平台

> 一句话：**员工打一句话，AI 就去真实地操作公司内部的业务系统。**
> 业务系统零改造接入（交一份 OpenAPI 接口文档即可），模型由平台统一供给，敏感操作人工确认。

---

## 1. 系统定位

**解决什么问题**：企业内部每个业务系统（预订、报修、审批……）想加上 AI 能力，各自对接一遍大模型——重复建设、成本分散、无法治理。

**方案**：建一个**统一的 AI 助手平台**，把"AI 怎么用工具"这件事收敛到一处：

- 对**业务系统**：零 AI 改造。不碰模型、不写 AI 代码，提供 OpenAPI 文档即可把接口注册为工具；自身有鉴权的系统需一次性对接可信调用通道（服务凭证或 SSO），见 §4.3；
- 对**员工**：一个入口。自然语言跨系统办事，过程全程可见；
- 对**平台**：模型统一供给、用量统一管控、危险操作统一拦截。

**不是什么**：不是智能客服（客服回答问题，本系统执行操作——产出是真实的数据库变更，不是一段话）；不跨企业边界（接入方须为本公司内部系统，员工走统一身份）；不是**可被任意前端直接复用的 AI 中间件**（原因见下）。

### 1.1 部署形态：统一入口，不是"AI 中间件"

当前是一套**员工统一入口**，不是被其他业务前端调用的中间件或 BFF：

```
员工浏览器 → 平台（登录 + 对话）→ 工具层 → 各业务系统
```

- 平台用自己的 `app_user` 签发 JWT，`index.html` 就是这个入口的**正式 UI**（对话、历史回放、工具轨迹、用量；管理员另有一个运维管理台），不是调试页。
- 业务系统自己的前端不受影响，继续服务不使用 AI 的场景；平台不代理、不嵌入这些前端。
- 业务系统只需暴露 OpenAPI。平台转发时附服务凭证与最终用户声明，业务系统对 AI 零感知。

**为什么不能直接叫作中间件**：中间件的前提是"别的系统把它当基础设施调用"，而调用方首先要回答"我是谁"。平台目前只认自己的账号体系，没有接受或校验其他系统登录态的能力；`X-On-Behalf-Of-User` 传的是**平台用户 id**，meeting-booking 只校验服务凭证、直接把它当作自己的 `user_id`——两边用户 id 在演示里靠"都从 1 开始"默认对齐，并不是真实的身份映射。在这两件事解决之前，它只能作为统一入口部署，不能承诺"任何前端接进来就能用"。

**嵌入式/中间件是另一个产品形态，本项目不做**（HTTP/SSE 接口形状已经具备，不需要重做运行时）。真要做，前提是先解决三件事：

1. **身份联邦**：接受企业 SSO 或其他系统的 token，或提供标准的 token 交换端点；
2. **用户映射**：平台用户 ↔ 各业务系统用户的映射表，替换当前"同 id"假设；
3. **调用方隔离**：会话与用量能回答"由哪个入口/哪个调用方发起"，管理端按调用方归属。

> 面试口径：定位按"统一入口"讲；被问到"能否给已有前端做嵌入式 AI"时，回答接口形状已具备，但身份联邦与用户映射不在本项目范围内——这是边界，不是未完成的半成品。

## 2. 总体架构

```
                    ┌───────────────────────────┐
                    │       用户（企业员工）        │
                    └─────────────┬─────────────┘
                                  │ 浏览器 · 一句话
                                  ▼
┌────────────────────────────────────────────────────────────────┐
│                    agent-platform（:8000）                       │
│                                                                │
│  ① 用户接入层【已实现】                                            │
│     员工登录(JWT=身份) → 每次请求回库加载角色/权限，在调用点强制校验          │
│                    │                                           │
│  ② Agent 运行时【已实现】                                         │
│     ReAct 显式循环：规划 → 工具调用 → 观察 → 反思 → 回答             │
│     SSE 分阶段直播 · 上下文裁剪 · Token 打点 · 敏感操作挂起等确认     │
│     内部工具本地执行：recallHistory（会话记忆）· search_knowledge（RAG）│
│                    │ ToolGateway（进程内方法调用）                  │
│  ③ 工具层【已实现】                                               │
│     OpenAPI → Tool 自动注册                                       │
│     闸门1 清单组装 · 闸门2 执行点鉴权 · 泛化 HTTP 转发               │
└─────────┬──────────────────┬──────────────────┬─────────────────┘
          ▼                  ▼                  ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
   │ 会议室预订系统 │    │  报销系统     │    │  报修系统     │
   │ （已接入·真实）│    │（已接入·模拟） │    │（已接入·模拟） │
   └─────────────┘    └─────────────┘    └─────────────┘
   ↑ 业务系统零改造：不碰模型、不写 AI 代码，只需提供接口文档（并可用扩展字段声明权限要求）

   模型：平台统一供给（OpenAI 兼容协议，yml 配置可换供应商）→ 只有 ② 用它
   Embedding：SiliconFlow bge-m3（与 chat 模型分离，因为聊天供应商没有 embeddings 接口）
   基础设施：MySQL（工具注册/会话/用量打点） + Postgres + pgvector（知识向量）
```

三个系统都在 `/v3/api-docs` 暴露契约，平台按来源注册表**持续对账**：启动时一次、之后默认每 5 分钟一次，也可手工触发——**"契约可访问"就等于"工具可用"**，且接口新增/修改/删除都会收敛，不必重启平台（ADR-008）。来源清单存在 `tool_source` 表：`platform.gateway.sources` 只是启动种子，管理员可在运行时 `POST/PUT/DELETE /admin/sources` 增删改（ADR-009 演进路径的第一步）；编辑过的来源归管理端所有，配置不再覆盖，移除来源会把它名下的工具软下线。两个模拟系统用 WireMock 实现，只写 mappings + 一份 OpenAPI，不写业务代码：它们的职责是提供"同一用户在不同系统权限不同"这件事的对照面（闸门 2 只有跨系统才有说服力），以及**失败语义的对照面**——它们和真实单体一样用标准状态码表达失败（缺身份 401 / 他人数据 403 / 目标不存在 404 / 状态不允许 409），而不是对任何输入都回 200。

**分层职责**：

| 层 | 职责 | 关键点 |
|---|---|---|
| ① 用户接入层 | 认识"你是谁"，把角色与权限带到执行点 | JWT 只带 uid；每请求回库加载 RBAC；`/admin/**` 按 URI 映射权限码；**不在这一层裁剪工具** |
| ② Agent 运行时 | 决定"怎么做"：选工具、造参数、看结果、定下一步 | 显式 ReAct 循环，每步可插桩（事件/确认/上限） |
| ③ 工具层 | 决定"怎么安全地做"：清单组装、执行点鉴权、转发 | 与 ② 同进程，`ToolGateway` 一次方法调用即达 |
| 业务系统 | 只提供接口（OpenAPI 文档） | 对 AI 零感知 |

## 3. 一次完整请求（业务流程）

用户输入："**帮我订下周三下午两点、能坐 8 人的会议室**"

```
用户                ② Agent 运行时           ③ 工具层            会议室预订
 │                        │                     │                     │
 │──"帮我订下周三…"──────▶│                     │                     │
 │                        │ 0. LLM 读工具清单      │                     │
 │◀─ plan(模型决策) ──────│                     │                     │
 │                        │ 1. listTools ──────▶│ 下发全部工具+权限声明   │
 │                        │◀── 工具清单 ─────────│                     │
 │                        │                     │                     │
 │                        │ 2. LLM 决策：先查房间（参数自填：              │
 │                        │    date=2026-10-07 由"下周三"换算而来）        │
 │◀─ plan/tool_call ──────│                     │                     │
 │                        │ 3. callTool ───────▶│ 4. 闸门2 + 转发 ─────▶│ 查库
 │                        │◀── 真实结果 ─────────│◀────────────────────│
 │◀─ tool_result ─────────│                     │                     │
 │                        │ 5. LLM 观察→反思：    │                     │
 │                        │    房间唯一满足→直接订 │                     │
 │                        │ 6. callTool(create) ────────────────────▶│ 写库
 │                        │                     │◀── 预订号 9 ─────────│
 │◀─ answer ──────────────│ "已订好 B401，预订号9" │                     │
 │◀─ done ────────────────│                     │                     │
```

注：`listTools` / `callTool` 是 `ToolGateway` 的进程内方法调用，不是网络往返——上图把它们画成一次"调用"只为标出职责边界。

**敏感操作分支（取消类工具 `require_confirm=true`）**：第 6 步前循环挂起 → 推 `confirm_request` 事件 → 用户点"同意/拒绝" → 恢复执行或把"用户拒绝"作为观察喂回模型。

**知识检索分支（平台内部工具）**：问题涉及制度、流程、标准时，模型调用 `search_knowledge`。它与 `recallHistory` 同构——不进工具层、不过闸门 2，由 `AgentRunner` 本地执行：query 向量化 → pgvector 相似度检索（权限过滤写进 SQL，无权内容不进候选集）→ 命中块作为观察回填。检索失败同样只返回文本观察，不打断循环（[KNOWLEDGE-RAG.md](KNOWLEDGE-RAG.md)）。

**错误自愈（实测）**：模型首次 `create` 时间格式错（`14:00:00`）→ 业务系统返回 400 → 模型自动改为 `14:00` 重试成功——工具失败包装为 `isError=true` 的文本观察交模型决策，不打断循环。

**前提是业务系统真的用非 2xx 表达失败**：`GenericHttpForwarder` 只以"非 2xx 或异常"判定 `isError`。业务系统若把业务异常也装在 HTTP 200 的响应体里（`{"code":1001,"message":"预订不存在"}`），平台拿到的就是一句正常的观察，模型于是把"该时段已被占用"读成"订好了"。业务码是给人排查用的，**状态码才是调用方判断成败的依据**；接口文档里要写明失败用哪些状态码。唯一例外是幂等重放——它返回的是既有记录，语义上属于成功，保持 2xx。

## 4. 用户权限：核心原则与三道闸门

### 4.0 权限模型：轻量 RBAC（单角色 + 角色-权限映射）

**JWT 只证明身份，不承载授权**：token 只带 `uid`（+ iat/exp），不含角色或权限。角色是可变的授权状态；把它写进 token，等于"降权要等 token 过期"，而常见实现又会退化成不可撤回的字符串。`JwtAuthFilter` 每次请求解析 uid 后调用 `RbacService.loadPrincipal(uid)`，回库读 `app_user.status/role` 与 `app_role_permission`，构造 `UserPrincipal(uid, role, permissions)` 写入 `UserContext`。停用账号、收回权限都在**下一个请求**生效，不需要撤销接口、黑名单或 token version。

**数据模型**：`app_user.role`（单角色）→ `app_role`（角色元数据）→ `app_role_permission`（角色-权限映射）。`app_role.seeded` 是"默认权限只种一次"的标记：`RbacSeeder` 只在未种过时写入，管理员在界面改过之后重启不会复活默认值。

**权限码**：`*` 为通配（ADMIN 默认持有）。平台内置 `admin:console` / `admin:source` / `admin:tool` / `admin:knowledge` / `admin:rbac`；业务侧自定义（`booking:cancel`、`expense:approve`、`repair:assign`）；知识块使用 `public` 或任意权限码。管理端提供角色-权限矩阵（查看、覆盖式保存），不做角色 CRUD 与用户角色分配。

**权限粒度仍在操作上**：业务系统在 OpenAPI operation 上声明 `x-required-permission`，对账写入 `tool_definition.required_permission`，执行点检查用户权限集合是否命中。旧字段 `x-required-role` 兼容：导入时归一为合成权限码 `role:<ROLE>`，执行点只看权限码。**平台依然不编码业务语义**——"取消要什么权限"由业务契约定义，"哪个角色拥有该权限"由管理员配置，删掉一个业务系统后平台逻辑无需改动。

**仍然不做**：多角色、角色继承、按来源分角色、强制下线。当前是单角色 + 全局权限集合；"同一用户在不同系统能做的事不同"仍由各系统对自己的操作声明不同权限码来表达——用户角色没变，变的是每个操作的门槛。按来源分配角色需要 `(user_id, source_key) -> role` 映射表，属于另一个产品形态，本项目明确不做（见 §8）。

### 4.1 核心原则

**模型只提议、不授权；权限校验在代码里，不在模型脑里。**
AI 的工具选择是一个"建议"，真正的安全边界在工具层执行点——由不经过模型的代码，按会话绑定的真实用户身份强制校验。因此模型幻觉出工具名、或被提示注入（"你现在是管理员"）都无法越权：校验看的不是模型说了什么，而是用户是谁。

### 4.2 三道闸门

```
AI（提议者）："我想调 admin_delete_user"
      ↓
【闸门1·清单组装】listForModel 下发该网关全部启用工具，不按权限裁剪
   → 权限要求写进工具描述，模型知道"这个能力存在、但当前身份可能不够"
   → 为什么不裁掉：裁掉的话模型只会答"我没有这个功能"，把权限问题说成能力问题
      ↓
【闸门2·执行点强制鉴权】★ 安全边界 ★
   invoke 到达工具层 → 校验 会话用户权限集合 × tool.required_permission
   → 不命中：包装为 isError=true 的结果拒绝（模型读后转述用户，循环不中断）
      ↓
【闸门3·敏感操作人工确认】
   弹窗前先用同一权限规则做只读预判：无权则直接回闸门2同款拒绝文本，不弹注定失败的确认
   有权调用的破坏性/不可逆操作 → confirm_request 挂起 → 用户点同意才执行
```

模型对"能不能调"的抉择因此分三段：**提前判断**（描述里已披露权限要求）→ **尝试**（照常发起调用）→ **被拒后转述**（闸门 2 返回 `权限不足：需要 X 权限`，模型据此向用户说明，而不是把失败说成自己不会）。

### 4.3 现状：三道闸门均已实现

- **接入鉴权**：用户 JWT 一套打天下——`/api/v1/chat`、`/api/v1/confirm`、`/api/v1/tools`、`/api/v1/sessions/**` 校验 Bearer token；`/admin/**` 再按 URI 映射权限码：`/admin/rbac` → `admin:rbac`、`/admin/knowledge` → `admin:knowledge`、`/admin/sources` → `admin:source`、`/admin/tools` → `admin:tool`，其余 → `admin:console`（403 输出"需要 X 权限"）。没有第二套凭证体系。
- **闸门 1 / 闸门 2**：都在 `gateway/registry/ToolAccessService`，被 `InProcessToolGateway` 调用，即 `AgentRunner` 调工具时的必经之路。
- **闸门 3**：`ConfirmManager` 挂起 + `POST /api/v1/confirm` 恢复（同意/拒绝/超时三态均已实测）。
- **权限要求从哪来**：业务系统在自己的 OpenAPI 里用扩展字段声明（`x-required-permission` / `x-require-confirm`），平台导入时读取。平台不猜测接口语义——"哪个接口要什么权限"是业务系统的契约，不是平台的业务知识。
- **角色权限从哪来**：`app_role_permission`，管理端 `GET/PUT /admin/rbac/**` 维护；登录响应与每次鉴权都按当前映射解析。
- **业务调用身份**：转发时按来源附服务级凭证 `X-Service-Key`，并带上 `X-On-Behalf-Of-User: {uid}` 声明"代表哪个最终用户"，业务系统据此把数据记在本人名下（仅在服务凭证校验通过时才采信该头）。
- **"零改造"的准确边界**：指业务系统**不写任何 AI 代码、对模型零感知**，只需要暴露 OpenAPI。但如果业务系统自身有鉴权，平台请求不会自动被放行——平台持有的是自己的 JWT，签名密钥与业务系统不同，直接转发会被对方 401。因此需要一个**一次性的身份通道适配**，二选一：① 业务系统认可平台的服务级凭证（本项目 meeting-booking 的做法：在 `JwtFilter` 里加一个服务凭证分支，约 20 行，并从 `X-On-Behalf-Of-User` 解析最终用户）；② 走企业 SSO / 令牌交换，让平台持有对方可信的身份。完全无鉴权的服务（如两个 WireMock stub）则确实只需一份契约。**这不是"零改造"，而是"零 AI 改造"**——安全通道的对接成本必须如实计算。

### 4.4 闸门 2 的核心实现

模型可能幻觉出不存在的工具名，也可能被提示注入诱导去调越权工具，因此执行前必须再校验一次。拒绝**包装为 `isError=true` 的文本结果**而非异常——模型读得到、循环不断：

```java
// ToolAccessService.invoke：定位工具后、转发之前
String required = tool.get().getRequiredPermission();
if (required != null && !required.isBlank() && !user.hasPermission(required)) {
    return new ToolCallResult(true, "权限不足：需要 " + required + " 权限");
}
```

`UserPrincipal.hasPermission` 命中规则只有一条：`permissions.contains("*") || permissions.contains(required)`。旧 `required_role` 行由导入阶段归一为 `role:<ROLE>`，执行点不再有第二套比较逻辑。

两道闸门的共同约定：**失败永不抛异常**，一律返回文本观察（`ToolCallResult.isError`）——这是 ReAct 循环能"看到失败并自己决定下一步"的前提。

### 4.5 一次越权尝试的完整流转

```
普通员工："帮我把 3 号预订取消"（cancel 要求 booking:cancel）
 ① 模型在清单里看得到 cancel，描述里标着"需要 booking:cancel 权限"
 ② 模型仍发起调用（或幻觉/被注入硬调）
 ③ ToolAccessService.invoke：STAFF 的权限集合不含 booking:cancel → isError=true 拒绝
 ④ 模型读到"权限不足" → 转述用户"这个操作需要相应权限"
 ⑤ （若权限已授予：走已有的 confirm_request 人工确认闸门）
```

### 4.6 AI 出错的分类对策（均已实现）

| 错误类型 | 机制 | 代码位置 | 状态 |
|---|---|---|---|
| 参数/格式错 | 错误回喂自纠 | `ToolAccessService.invoke` isError 包装 + 系统提示词 | ✅ 实测（400 时间格式 → 自改重试成功） |
| 死循环 | 步数熔断 | `LoopGuard`（maxSteps=8） | ✅ |
| 有权但危险 | 人工确认闸 | `require_confirm` 列 + `ConfirmManager` 挂起 | ✅ 实测三态 |
| 重复写入 | 语义幂等键 | booking SHA-256(userId\|roomId\|date\|…) | ✅ 实测 |
| 越权调用 | 闸门 2 执行点鉴权 | `ToolAccessService.invoke` | ✅ |

> 设计原则：**接入零成本，授权有边界**。技术上接一个新系统只需导入 OpenAPI；治理上必须回答"谁能用、以谁的身份、留什么痕"。

## 5. 模型策略

- 模型**只被 Agent 运行时使用**（工具层、业务系统均不依赖 LLM）；
- 平台统一供给：OpenAI 兼容协议，`yml` 配置供应商（默认 DeepSeek，`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` 三个环境变量一改即切厂商）；
- Embedding 独立配置（默认 SiliconFlow `BAAI/bge-m3`）：聊天供应商不提供 embeddings 接口，两者不能共用同一组凭证；未配置 key 时知识库整体不装配；外部调用带 3s/20s 超时与指数退避重试（仅可恢复错误），用量按模型计入 `knowledge_usage`；
- 演进路径：单模型（现状）→ 模型配置入库热切换 → 按接入方/场景路由不同模型（触发条件：成本分摊或需求分化）。

## 6. 关键设计决策（详见 docs/adr/）

| 决策 | 一句话理由 |
|---|---|
| 滑窗 + 摘要混合裁剪（ADR-003） | 纯滑窗丢关键事实、纯摘要成本翻倍；实测总 Token 降 31.8%，代价 +48.8% 重查次数 |
| 工具前置路由接口先行、默认休眠（ADR-004） | 工具数未达阈值时整链休眠、全量直通——规模化前零开销，规模化后自动武装 |
| 会话记忆用内部工具调回而非 RAG（ADR-005） | 对话消息短碎、上下文依赖强，嵌入质量天然差；把 RAG 推迟到规模证明它必要的时刻 |
| 进程内工具调用，删除 MCP 协议层与自环（ADR-006） | 自环理由只有"预留拆分部署"且从未兑现，代价是每次调用多一跳网络、异常跨协议层 |
| 权限要求与工具来源从业务契约读取（ADR-007） | 权限码/敏感度由业务方声明、契约启动时自动拉取——平台不编码业务语义，接入方零改平台 |
| JWT 只证明身份，授权每次回库（ADR-010） | 角色/权限是可变的服务端状态；写进 token 意味着降权要等过期，且无法撤回 |
| 契约按来源做快照对账（ADR-008） | 每轮拿契约推导的期望状态与库内状态收敛：新增/更新/软下线；`present` 与人工 `enabled` 分离，失败保留 last-known-good |
| 来源静态配置 + 主动轮询（ADR-009） | 变更源不在业务进程内，推模型要求业务改造；拉模型天然自愈。发现层与对账层解耦，演进路径见 ADR-009 |
| 知识库 RAG 与会话记忆分治（KNOWLEDGE-RAG.md） | 对话历史短碎、上下文依赖强，语义检索收益低；制度文档长且有结构，适合按标题切块 + 向量检索 |

## 8. 非目标：为什么不做成生产级通用网关

> 这一节列的是**明确的非目标**，不是待办清单。本项目只把"存量系统接入 AI"这一条路径做透；下面这些能力每补一项，都会牵出一整套配套（身份映射、按用户凭证缓存、审核流程），项目就会从"接入模式演示"变成半成品通用网关。面试时按这个口径回答，不要声称"任意 OpenAPI 零改造接入"。

### 8.1 不做契约导入策略：全量导入是刻意的

**现状**：一份契约里所有 paths × 5 种 HTTP 方法都会成为工具，且新工具默认 `enabled=1`。平台不做 tag 过滤、不做 `deprecated` 过滤、不区分 `/internal`、`/admin` 等路径，也没有导入审批。

**为什么这样选**：它让"契约可访问 = 工具可用"在演示与开发环境里成立——接入方只维护契约，不维护第二份工具清单；也避免手工导入产生没有来源归属、不参与对账的幽灵工具。

**生产上会有什么问题**（仅作认知，不是本项目要修的 bug）：

- 内部接口、调试接口、管理接口会被一并暴露给模型；
- 大契约让工具清单膨胀，降低模型选工具准确率并抬高每轮 token；
- 新上线的接口在无人复核的情况下自动获得 AI 调用能力；
- 目前唯一的收敛手段是管理员在工具目录里逐个禁用——粒度太细、成本太高。

**如果将来真要做产品化，前提是先解决这些（本项目不做）**：

1. **契约侧声明**（平台只需读）：约定 `x-ai-exposed: false`，或只导入指定 tag/group。平台增加一个 opt-out 扩展字段即可，仍是"业务声明、平台执行"，不违背平台不编码业务语义的原则。
2. **来源级策略**：登记来源时配置 allowlist/denylist（tag、路径前缀或 operationId 正则）。这是部署配置，不是业务语义。
3. **导入即待审**：新工具默认 `enabled=0`，管理员确认后才启用；可做成来源级开关 `auto-enable-new-tools`，演示环境打开、生产关闭。这需要把"新工具默认启用"的当前行为改掉，是这一项里唯一有数据库/对账语义变化的改动。
4. **规模化后启用已有路由链**：`ToolSelector` 在工具数达到阈值时自动接管，缓解"选得准"的问题，但它不解决"该不该暴露"。

**本项目的选择到此为止**：保留全量导入 + 自动启用，把边界写清楚，不实现上面 1/2/3。简历里描述为"基于契约的全量工具注册"，不要描述为"已具备导入治理"。

### 8.2 不做异构鉴权：只支持静态服务凭证

**现状**：`GenericHttpForwarder` 只会给每个来源附**一个静态请求头**（`tool_definition.auth_header_name/value`，如 `X-Service-Key`），外加 `X-On-Behalf-Of-User`。没有任何按用户获取或刷新凭证的能力。`meeting-booking` 能接入，是因为它自己加了一个服务凭证分支；两个 WireMock stub 则完全没有鉴权。

| 后端形态 | 现状 | 缺什么 |
|---|---|---|
| 静态服务密钥 | 支持 | — |
| 用户 JWT 透传 | 不支持 | 平台 token 与业务 token 签发方不同，需要令牌交换或共享签发 |
| Cookie / Session | 不支持 | 登录握手、Cookie 容器、过期续期、按用户隔离 |
| OAuth2 client credentials | 不支持 | token 获取 / 缓存 / 刷新与失败重试 |
| HMAC / mTLS 签名 | 不支持 | 按请求体与时间戳计算签名、双向证书 |
| 多请求头 / 多值 | 只支持一个 header | 可配置的 header 集合 |

**如果将来真要做，方向是**把"怎么证明调用方身份"从转发器里抽出来，做成来源级 `AuthStrategy`：`NONE` / `STATIC_HEADER` / `FORWARD_USER_TOKEN` / `OAUTH2_CLIENT_CREDENTIALS` / `LOGIN_SESSION`。策略在转发前注入 header 或 cookie；平台仍然只负责编排与执行点鉴权，不解释业务语义（**本项目不实现**）。**身份映射**（平台用户 ↔ 各业务用户）与 §4.0 的"按来源角色"属于同一类问题，应一起设计，否则 `X-On-Behalf-Of-User` 只能在用户 id 空间碰巧对齐时成立。

**面试口径**：这是明确的非目标，不是未完成的功能——当前只把静态服务凭证这一条路径走通；异构鉴权与按来源角色属于另一个产品形态，不在本项目范围内。

> 以上边界问题的完整追问与回答整理见 [docs/highlights/05-boundaries-and-tradeoffs.md](highlights/05-boundaries-and-tradeoffs.md)。
