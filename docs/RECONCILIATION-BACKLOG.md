# 契约对账：已知缺口与处理计划

> 来源：2026-10-20 关于服务发现、轮询与对账边界的讨论。按"是否影响正确性/安全/可用性"分组，实施状态随代码更新。
>
> 范围说明：只描述**契约来源与对账**链路。与业务语义、模型效果相关的问题不在此列。

## 状态总览

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | 手工触发与定时对账并发，可能记假 `FAILED` | 观测失真 | 已实施 |
| 2 | 来源下线后其工具不下线，成为孤儿 | 模型仍能看到已下线接口 | 已实施 |
| 3 | 先确认、后鉴权，无权限用户也要点一次确认 | 体验瑕疵，安全无害 | 已实施 |
| 4 | 来源 `id` 缺省时按 host+port 兜底，键不稳定 | 一份契约被算成两份 | 已实施 |
| 5 | 对账只有日志，没有指标与告警 | 排障靠翻日志 | 已实施 |

## 1. 对账并发

**现状**：定时任务自身是 `fixedDelay`，不会重入；但手工 `POST /admin/sources/sync` 可与定时任务或另一次手工调用撞车。两个线程同时抓同一契约、同时写库，后完成者可能撞唯一键，被外层 `catch` 记成 `FAILED`——实际已成功。

**处理**：对账入口使用进程内 `ReentrantLock.tryLock`。抢不到锁的一方直接返回 `BUSY` 报告，不排队、不写库。锁覆盖整个"抓取 → 解析 → 落库 → 记状态"过程。

**边界**：进程内锁只在单实例有效；多实例见第 10 项。

## 2. 来源下线后的工具收殓

**现状**：从 `platform.gateway.sources` 删除一个来源后，平台不再抓取它，但 `tool_source` 行与工具保持 `present=1`，模型清单里仍然可见。临时宕机保留 last-known-good 是正确的；永久下线则缺少收殓。

**处理**：

- 每次启动以配置为准做来源种子：配置中已消失的 `CONFIG` 来源标记 `RETIRED`，其名下工具 `present=0`（软下线，不删行）；
- 管理端删除来源同样是软下线：`status=RETIRED`、`enabled=0`，工具立即从模型清单消失；
- 来源重新出现时自动复活，下一轮对账把工具恢复为 `present=1`。

## 3. 确认与鉴权的顺序

**现状**：`AgentRunner` 看到 `require_confirm` 先挂起等用户确认，用户同意后才进入 `ToolAccessService` 的闸门 2。无权限用户会先看到一个注定失败的确认弹窗。

**处理**：弹确认之前先做**只读角色预判**（`ToolAccessService.denial`）。角色不足直接返回闸门 2 同款拒绝文本，不弹确认；预判通过后仍照常进入确认与执行。原则：**预判只能跳过确认，不能替代执行点鉴权**。

## 4. 来源标识必须显式

**现状**：未配置 `id` 时用契约 URL 的 host+port 兜底。平台在容器内外访问同一后端时 host 不同（`localhost` vs `host.docker.internal`），会被算成两个来源。

**处理**：`id` 改为必填。启动时校验非空且唯一，缺失直接启动失败并指出具体条目；删除兜底逻辑。管理端新建来源同样必填。

## 5. 对账可观测性

**现状**：成功/失败/耗时/破坏性变更只写日志，排障要翻日志或轮询 `GET /admin/sources`。

**处理**：接入 Micrometer（已有 actuator + prometheus）：

- `platform.contract.sync`：计数器，tag `source` / `result`（OK / FAILED / CONFLICT / BUSY）；
- `platform.contract.sync.duration`：计时器，tag 同上；
- `platform.contract.breaking`：破坏性变更计数器，tag `source` / `type`。

通知渠道（邮件/webhook）不在本次范围。

## 6. 管理端来源注册表

**现状**：来源只存在于配置文件，新增/编辑/删除都要改配置并重启。ADR-009 已把"DB 注册表"列为演进第一步。

**处理**：`tool_source` 升级为来源注册表，配置文件退化为**启动种子**（每次启动按配置刷新 `CONFIG` 来源）。

**语义边界（重要）**：管理员登记的是**来源**，不是工具。

- 可编辑：来源标识、契约地址、调用基地址、服务凭证、启停；
- 不可编辑：工具名、描述、参数 schema、角色要求、敏感标记——这些永远由契约推导，管理端只读，工具只能启停；
- 凭证只入不出：查询接口只返回 `serviceKeyConfigured`，不回显任何片段。

**配置与数据库的所有权规则**：

- 配置里出现的来源首次启动时写入，`origin=CONFIG`；
- `origin=CONFIG` 的来源每次启动按配置刷新；从配置移除则软下线；
- 管理员编辑过的来源提升为 `origin=ADMIN`，此后配置不再覆盖它；
- 管理员新建/删除只影响 `origin=ADMIN`（删除 CONFIG 来源会因下次启动种子而复活，API 直接拒绝）。

**接口**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/sources` | 列表（状态、差异计数、凭证是否配置，不回显值） |
| POST | `/admin/sources` | 新建来源并立即对账 |
| PUT | `/admin/sources/{sourceKey}` | 编辑契约地址/基地址/凭证/启停 |
| DELETE | `/admin/sources/{sourceKey}` | 软下线来源与工具 |
| POST | `/admin/sources/{sourceKey}/sync` | 立即对账 |
| POST | `/admin/sources/sync` | 全部对账 |

## 7. 工具名冲突（已实施最小版）

同一 `gatewayId` 下工具名是全局命名空间。多个系统共用一个 `gw1` 才能在一次对话里跨系统聚合，代价是 `operationId` 重名时整份快照放弃、该来源全部工具停止更新。

**处理（最小版）**：不改命名空间、不按来源加前缀、不做"只跳过冲突工具"——冲突仍是整份放弃，但把定位信息暴露出来。`applySnapshot` 抛出的消息包含冲突工具名与占用来源，对账把来源标 `CONFLICT` 并写入 `tool_source.last_error`；`GET /admin/sources` 原样返回该列，管理界面直接展示。管理端无需翻日志就能回答"谁和谁冲突、要改哪份契约"。

**明确边界**：`last_error` 是观测信息，不是自动修复——平台不会替接入方改名，也不会因为某个工具冲突而部分写入其余工具。

## 8. 手工导入的幽灵工具（已实施）

`POST /admin/protocols/import` 与 `ToolRegistryService.upsertAll` 已删除。工具定义只有一条写入路径：来源注册表登记来源 → 对账拉契约 → `applySnapshot`。没有来源归属的工具不再可能产生。

现在新增系统必须登记来源（`POST /admin/sources` 或配置文件种子），接入方式从"交一份文档"收敛为"登记一个持续可访问的契约地址"。

## 9. 5 分钟轮询（接受）

契约只在发版时变化，轮询天然自愈。演进方向是 CI 回调 + 轮询兜底，见 ADR-009。

## 10. 多实例（接受）

重复抓取、事件仅进程内、确认项内存态。触发条件是真正部署多副本；见 ADR-008 第 9 条与 ADR-009 第 5 条。

## 11. 测试缺口

现有对账测试为 Mockito 单测，覆盖并发触发、来源下线收殓、注册表 CRUD、冲突详情与凭证不回显。另补了 HTTP 层 `ToolSourceAdminControllerTest`（9 项，standalone MockMvc）：400 参数校验、404 不存在、409 重复/配置来源下线、以及"只披露 `serviceKeyConfigured`、不返回凭证值"。仍缺（可选）：真实 MySQL 上的 `schema.sql` 幂等与 CRUD 集成验证。

## 12. 管理界面（已实施）

控制台顶栏的「来源管理」抽屉（需 `admin:source` 权限；拥有 `admin:console` 即可打开管理台）复用 `/admin/sources`：列表展示状态、工具数、上次成功时间、凭证是否配置与完整 `lastError`；支持新增、编辑（凭证留空保持原值）、立即对账、二次确认下线。契约冲突时抽屉里直接看到"工具名 + 占用来源"，不必查日志。
