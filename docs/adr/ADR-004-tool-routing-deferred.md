# ADR-004：工具前置路由（System One 决策模型）——接口先行，路由器默认关闭

日期：2026-09-30　状态：已采纳（接口就位，路由器默认透传）

## 背景

随着业务系统持续接入，网关工具集将线性增长。全量 Schema 暴露给主模型会带来三类问题：
prompt 膨胀、首字延迟上升、多工具选择幻觉（工具超过约 20 个时显著）。

社区同期出现了"System One 决策模型"范式：用小型/专用模型在主推理前做毫秒级结构化判断
（从候选工具中选一个），替代"把全部 Schema 倒给主模型"。代表产品 TypeSafe AI Jev
（2026-09-21 发布，early access 托管 API）。

## 考察过的选项

| 选项 | 评估 |
|---|---|
| TypeSafe AI Jev（托管 early access） | 产品真实（官方公告/三方报道已核实），但①仅托管 API、无可自托管权重（"开源"说法未获官方证实）；②waitlist 放人中，演示可用性无保证；③Java 需自对接（官方仅 Python wrapper） |
| **wattai（开源平替，Apache-2.0）** | ✅ 已采纳为路由器实现：同范式（state+questions→校准概率）、可自托管（GGUF：205MB 量化 / 17MB LoRA，蒸馏自 SmolLM2-360M）、托管端点免费（匿名 1000 次/天）；基准为厂商自测需自证 |
| 本地语义路由（嵌入相似度） | 零依赖备选，未实施 |

## 真实探测数据（托管端点 api.wattai.dev v0.5，2026-09-30）

用平台真实 7 工具 + 真实中文用户话术探测：

- 延迟：**~2s/次**（含跨境网络；自托管 GGUF 预期 <100ms）
- 路由质量：两轮不同意图（预订 vs 查列表）分布几乎相同，其中"查看预订列表"被误路由到 `create`（置信度 0.38）——360M 蒸馏模型对中文语义 + 英文工具名的区分不足
- 置信度持续低于 0.6 阈值 → 按降级策略全部回落 top-k/全量

## 决策

1. **落地 `ToolSelector` 扩展点 + 两种实现**（Noop 默认透传 / WattAi 路由器），配置切换；
2. **WattAiToolSelector 默认关闭**（`platform.agent.tool-selector: noop`）：当前 7 工具规模下路由收益为负（+1 跳 2s 网络、决策质量不足）；
3. 触发启用条件（任一）：接入工具 >20；自托管 GGUF 部署消除网络延迟；wattai 托管端点质量改善；
4. 启用后必须 A/B 实测（prompt tokens / TTFT / 路由准确率）并回填数字——不引用任何厂商声明。

## 后果

- 正面：扩展点就位，工具规模化时切换成本≈一行配置；探测数据与决策过程留档。
- 负面：多维护一个"默认关闭"的实现类与其测试；System One 范式仍在快速演进（Jev/wattai 均为 v0.x），需周期性重评估。

## 修订（2026-10-02）：策略单选升级为责任链

原"配置单选 Noop/WattAi"重构为责任链装配（`ToolSelectorChain`），决策 3 的"触发启用条件"由人工记忆变为自动机制：

1. **规模闸门**：工具数达到 `platform.agent.routing.tool-count-threshold`（默认 20）整链才启用，未达则休眠、全量直通——个位数工具规模下对主流程零开销，规模化后自动武装；
2. **节点有序 + 弃权传递**：`routing-handlers`（默认 `wattai`）按序装配，节点返回 `Optional.empty` 即弃权（前置不满足/决策不可信/调用失败）传下一环，节点抛异常同样降级不阻断；预留 jev（TypeSafe AI Jev 托管 API）与本地语义路由扩展位，实现就绪后在 `AgentConfig` 按优先级追加一行即可；
3. **链尾兜底**：全部弃权 → 全量直通，与"不路由"等价——路由层故障永不进主流程；
4. 顺手修复潜伏缺陷：argmax 返回候选外工具名时，旧实现会交出**空工具集**（主模型无工具可用），现按弃权交链尾兜底处理（回归测试 `argmaxOutsideCandidatesAbstainsInsteadOfEmittingEmptySet`）。

"默认关闭"语义从"配置选 noop"变为"阈值未达自动休眠"：功能常在链路上，当前规模不产生任何额外开销。`NoopToolSelector` 由空责任链 + 链尾兜底自然取代，已删除。
