# ADR-005：会话记忆采用"内部工具调回"而非 RAG

日期：2026-10-02　状态：已采纳

> 本文只留决策记录；"为什么不用 RAG"的完整工程论证（嵌入对象质量、成本模型、
> 召回决策权、演进路径与重评估触发信号）见 `docs/MEMORY-STRATEGY.md`。

## 背景

ADR-003 的混合裁剪把早期对话压成确定性摘要，具体结论不可还原，代价已量化（激进裁剪重查询 +48.8%）。这个代价里有两类不同性质的信息：

- **业务事实**（房间号、预订状态）：权威源在业务系统，模型经业务工具重查即可——重查询是"多花一次调用"，不是"任务失败"；
- **只存在于对话中的信息**（用户口头偏好、临时约束、"刚才说过的那个"）：业务系统查不到，裁剪即永久丢失；跨会话记忆目前为零。

## 考察过的方案

| 方案 | 评估 |
|---|---|
| RAG（历史向量化检索） | 需要嵌入调用 + 向量库 + 切块与检索质量评估；对话消息短碎、上下文依赖强（"就订那个"无法单独嵌入），单条消息检索质量差；当前单会话 ≤30 轮规模下收益低于成本（与 ADR-003 结论一致，规模未变） |
| 全量不裁剪 | 放弃 31.8% 的 Token 收益，成本线性膨胀 |
| 每轮 LLM 摘要替代规则摘要 | 每轮多一次 LLM 调用，成本延迟双翻倍且引入不确定性（ADR-003 已否） |
| **内部工具调回（agentic recall）** | ✅ 采纳：数据层已就绪（chat_message 全量落库 + checkpoint），检索成本从"每条消息一次嵌入"降为"缺了才查一次"，召回决策权在模型 |

## 决策

新增平台自有内部工具 `recallHistory`（`agent/memory/impl/HistoryRecallTool`），会话记忆三层化：

1. **热**：最近 6 条消息原样在上下文（ADR-003 不变）；
2. **温**：checkpoint 里程碑摘要落库存档；
3. **冷**：chat_message 全量历史原文，`recallHistory` 按关键词检索取回（MySQL LIKE 起步，不引入向量库；跨表按时间正序合并，条数/单条长度有上限防膨胀）。

定位约束（硬性）：

- **领域中立**：只查对话历史，不含任何业务语义——换业务线该工具原样可用；
- **角色无关**：只查当前 sessionKey 的数据（自己的历史），天然无越权面，不走网关的角色/确认闸门；
- **平台自有**：不进 MCP 网关、不参与工具路由责任链（始终在册），由 AgentRunner 本地执行分派；
- **何时调回由模型判断**：工具 description + 系统提示词规则引导（"之前/上次/刚才"而上下文没有 → 调用），检索不到如实回喂，禁止编造。

## 后果

- 正面：裁剪丢细节从"不可恢复"变为"多一跳检索"；"关键结论以里程碑形式保留"从审计语义升级为可取回语义；演进路径（跨会话用户级记忆、MySQL 全文索引、规模后换向量检索）在数据层已就绪，工具契约不变。
- 负面：LIKE 检索无语义匹配能力，召回质量依赖关键词质量（模型可重试换词缓解）；模型可能多一轮工具调用（延迟换来准确性）；跨会话记忆仍未覆盖（既定演进项，需先定义用户级记忆的归属与清理策略）。
