# ⑤ 边界与追问：哪些是生产级，哪些只是演示

> **30 秒版本**：这个项目刻意只走"存量系统接入 AI"这一条路径。四篇亮点里，凡是核心链路（执行点鉴权、契约对账、显式循环、知识检索）都尽量做到了接近生产；凡是横向扩展与平台治理（多实例状态、导入审批、凭证托管、审计配额）都只做到演示级，并且都有明确的触发条件与补齐方案。
>
> 一句话原则：**承认没做，不等于承认没想过；把"没做"说成有意的范围控制，比堆一个半成品更有说服力。**

---

## 1. 契约全量导入

**问："OpenAPI 里所有接口都加载成工具，内部接口不也暴露了？"**

- **现状**：所有 `paths` × 5 种方法全量导入，新工具默认 `enabled=1`，没有 tag/路径过滤和导入审批。
- **为什么这样选**：契约是唯一事实来源，平台不维护第二份工具清单，也不会出现"手工导入但没有来源归属"的幽灵工具；"契约可访问 = 工具可用"这个等式才成立。
- **生产要补什么**：三种做法，按成本从低到高——① 契约侧 `x-ai-exposed: false` 或只导入指定 tag；② 来源级 allowlist/denylist；③ **导入即待审**，新工具默认 `enabled=0`，管理员确认后启用。
- **为什么本项目不做**：每一种都要引入治理面（审核 UI、策略配置、状态流转）。项目的目标是演示接入模式，不是做 API 治理平台。
- **高分句**：*"如果真上生产，我会改的不是'多几个禁用按钮'，而是默认值——AI 能力应该像权限一样默认关闭，导入后待审，而不是默认打开再一个个关。"*

**问："现在只能管理员一个一个禁用，粒度是不是太细？"**

- 手工禁用只是**逃生阀**，不是治理模型。真正的治理在导入策略和默认状态；逐工具启停只是兜底，不应该承担批量收敛的职责。

## 2. 权限模型与 RBAC

**问："这是 RBAC 吗？"**

- **现状**：轻量 RBAC。单角色（`app_user.role` → `app_role`）+ 角色-权限映射（`app_role_permission`），业务契约用 `x-required-permission` 声明操作门槛（如 `booking:cancel`），执行点检查用户权限集合是否命中；`*` 为通配。管理端提供角色-权限矩阵（查看、覆盖式保存），不做角色 CRUD 与用户角色分配。JWT 只带 `uid`，授权每请求回库，降权在下一个请求生效（决策 10）。
- **为什么这样选**：单租户、小规模，但"谁能做什么"需要可运营——把角色写死进代码或 token，改一次权限就要发版或等 token 过期。完整 IAM 的多角色、角色继承、强制下线仍不做：它们需要更多表与配套流程，而当前场景没有对应需求。
- **高分句**：*"RBAC 的核心不是角色表，而是把权限和业务动作解耦。权限码由业务契约声明、由管理员映射到角色、在执行点强制校验；我不做的是多角色继承与强制下线，因为它们服务于另一个产品形态。"*

**问："同一个人在这个系统是管理员、在另一个系统不是，怎么支持？"**

- **先纠正前提**：当前**不支持**这种模型。同一个全局角色对所有来源生效，不存在按来源分配角色。
- **"不同系统权限不同"的准确含义**：各系统对自己的操作声明了不同的权限门槛。STAFF 在 booking 能创建预订（未声明权限）、不能取消（声明 `booking:cancel`）；在 expense 能提交报销、不能审批。变的是操作门槛，不是用户角色。
- **如果产品真的需要按来源角色**：在现有角色-权限表之外再加 `(user_id, source_key) -> role` 映射，闸门 2 按来源取权限并集；契约已经用 `x-required-permission`，不需要再改。
- **为什么不做**：它同时牵出用户映射、管理 UI、知识库按来源可见性。属于另一个产品形态。

**问："业务系统自己不做权限校验，安全吗？"**

- 业务系统只**声明**，平台在闸门 2 **强制校验**；业务系统自己的 `user.role` 不参与授权（meeting-booking 的 role 列没有代码使用）。
- 好处：权限策略收敛到平台一处，业务系统对 AI 零感知；坏处：平台必须承担全部授权责任，闸门 2 是唯一安全边界，模型幻觉或提示注入都无法绕过。
- 前提是平台的 JWT 不可伪造：`JWT_SECRET` 缺失或不足 32 字节直接拒绝启动，仓库没有默认密钥。

## 3. 异构后端鉴权

**问："一个后端是 JWT，一个是 Cookie，一个是 Session，请求头也不一样，怎么接？"**

- **现状**：只支持一种——每个来源一个静态请求头（`X-Service-Key`），外加 `X-On-Behalf-Of-User`。没有按用户取 token、Cookie 容器、OAuth2 刷新、HMAC/mTLS，也**没有给契约拉取本身配凭证**。
- **为什么 meeting-booking 能通**：它自己加了服务凭证分支（约 20 行）；两个 WireMock 能通是因为根本没有鉴权。
- **生产方向**：把"怎么证明调用方身份"从转发器里抽成来源级 `AuthStrategy`：`NONE / STATIC_HEADER / FORWARD_USER_TOKEN / OAUTH2_CLIENT_CREDENTIALS / LOGIN_SESSION`。策略在转发前注入 header 或 cookie；契约拉取凭证（fetch credential）单独一套，不与调用凭证混用。
- **为什么不做**：每多一种鉴权，就多一套按用户凭证缓存、过期续期、失败重试和身份映射。项目会从"接入模式演示"变成半成品通用网关。
- **高分句**：*"接入成本不是零，准确说是'零 AI 代码 + 一次性的身份通道适配'。我会把鉴权策略抽出来，而不是在转发器里堆 if-else。"*

**问："平台的请求不会被业务系统直接拦截吗？"**

- **会**。平台 JWT 和业务 JWT 是两套签发方与密钥，直接转发必然 401。
- 所以需要一次性适配：服务凭证分支，或企业 SSO / 令牌交换。
- 服务凭证的安全要求：强随机、环境变量注入、可轮换；`X-On-Behalf-Of-User` **只在服务凭证校验通过后才采信**，否则任何人都能伪造"代表谁"。当前服务凭证明文落 MySQL，管理端只写不回显；生产应接 KMS/Vault。

**问："`X-On-Behalf-Of-User` 传的是谁的 id？"**

- 当前传的是**平台用户 id**，业务系统直接当作自己的 `user_id`。两边 id 空间在演示里靠"都从 1 开始"对齐，不是真实映射。
- 生产必须引入用户映射表；这也是"按来源角色"要一起设计的原因——两者都缺同一个 `(平台用户, 业务系统用户)` 关系。

## 4. 部署形态与多实例

**问："这是中间件还是统一入口？别的系统能接吗？"**

- **现状是统一入口**：员工登录平台、在平台对话；业务系统自己的前端照常服务不用 AI 的场景。
- 接口形状（`/api/v1/chat`、`/confirm`、`/sessions`）具备被其他前端调用的可能，但缺**身份联邦**和**用户映射**，所以现在不能承诺"接进来就能用"。
- **高分句**：*"它是一个完整的入口产品，不是一个半成品的中间件。边界清楚比能力多更重要。"*

**问："零改造是不是宣传话术？"**

- 准确说法是**零 AI 改造**：不写 AI 代码、不碰模型、只提供 OpenAPI。
- 但身份通道不是零成本：有鉴权的系统必须一次性对接（服务凭证或 SSO）；无鉴权的服务才是真正只给一份契约。
- **高分句**：*"我不会说'任何系统零改造接入'，我会说'零 AI 代码，加上一次性的身份通道适配'。后者更准确，也更经得起追问。"*

**问："多实例部署时，契约对账会打架吗？"**

- **不会写坏，但会重复干活。** `ContractSyncServiceImpl` 用进程内 `ReentrantLock` 防同一实例的并发对账；多实例之间没有互斥，每个实例都会各自抓契约、各自对账。
- 对账本身是幂等的（同一份快照收敛到同一状态），所以不会产生错误数据；代价是**重复抓取**与**日志噪声**。另一个实例在管理端点"立即同步"后，其他实例的工具缓存刷新也不是跨实例的——各实例按自己的轮询周期收敛。
- 生产补齐：给 `tool_source` 加租约/选主（如 `lease_until` 列 + CAS），同一时刻只允许一个实例抓取；变更事件走消息总线或共享缓存失效。
- **不要说**"有分布式锁"——现在没有，说清楚是单实例锁 + 幂等对账。

**问："确认项和会话锁在多实例下还有效吗？"**

- 都**只在单实例内有效**。`ConfirmManager`、`SessionLockRegistry`、`LoginThrottle` 都是进程内内存实现。
- 多实例下：确认请求可能落到另一实例（恢复不了，最终超时拒绝）；同一会话可能被两个实例同时处理；登录限流形同虚设。
- 生产补齐：挂起项入共享表 + CAS；会话锁用 Redis/行锁；限流用集中计数。删除这些内存态组件时要注意：**语义安全优先**——确认项丢失应按拒绝处理，不能按通过处理。

## 6. 不会答时怎么收口

不要编，也不要只说"没做"。用这三句：

1. **"这块当前没实现，我停在 X，因为 Y。"**
2. **"如果要做，我会先做 A，因为它解决的是根因，而不是加一个开关。"**
3. **"这会牵出 B 和 C，所以我判断它超出了这个项目的范围。"**

面试官要的是判断力，不是功能清单。**能说清"为什么不做"，和说清"怎么做"一样值钱。**
