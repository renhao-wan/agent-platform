# 亮点 ①：三道权限闸门——AI 越权防护

> 一句话：**模型只提议、不授权；权限校验在代码里，不在模型脑里。**
>
> 代码入口：`gateway/registry/ToolAccessService`、`agent/auth/JwtAuthFilter`、`agent/confirm/ConfirmManagerImpl`
> 背景决策：`docs/decisions/07-契约驱动授权.md`、`docs/architecture/ARCHITECTURE.md §4`

## 1. 30 秒版本

大模型可能幻觉出不存在的工具，也可能被提示注入诱导去调管理员接口。平台把"能不能做"拆成三道闸门，其中只有第二道是安全边界：

| 闸门 | 位置 | 做什么 | 是否安全边界 |
|---|---|---|---|
| 1 清单组装 | `listForModel(gatewayId)` | 下发**全部启用工具**，不按权限裁剪；权限要求写进工具描述 | 否，体验优化 |
| 2 执行点鉴权 | `invoke(...)` | 用**请求时回库加载的权限集合**与工具声明的 `required_permission` 比对，不命中即拒绝 | **是** |
| 3 人工确认 | `ConfirmManager` + `POST /api/v1/confirm` | 敏感操作挂起，用户同意才执行，超时视为拒绝 | 否，防误操作 |

拒绝不抛异常：工具层返回 `ToolCallResult(isError=true, text)`，循环把文本作为观察回喂模型（转发失败带 `tool error:` 前缀）。模型读得到、能向用户转述，ReAct 循环不中断。

授权数据来自轻量 RBAC：JWT 只带 `uid`，`JwtAuthFilter` 每次请求回库读取 `app_user.role` 与 `app_role_permission`，构造 `UserPrincipal(uid, role, permissions)`。降权/停用在下一个请求生效（决策 10）。

身份本身也做了最低限度的加固：`JWT_SECRET` 不足 32 字节直接拒绝启动（HS256 下限，仓库无默认密钥）；密码用 PBKDF2-HMAC-SHA256 存储；登录失败 5 次/5 分钟限流。这些不是亮点本身，但缺了它们，"执行点鉴权"就建立在一个可伪造的身份上。

## 2. 一次越权的完整流转

```
staff01："帮我把 3 号预订取消"（cancel 声明 x-required-permission=booking:cancel）
 ① 模型在清单里看得到 cancel，描述里已标"需要 booking:cancel 权限"
 ② 模型发起调用（正常尝试，或被注入后硬调）
 ③ ToolAccessService.invoke：STAFF 的权限集合不含 booking:cancel
 ④ 返回 isError=true 文本："权限不足：需要 booking:cancel 权限"
 ⑤ 模型转述："这个操作需要相应权限"
```

同一句话换成已被授予 `booking:cancel` 的角色，则 ③ 放行、进入闸门 3（如果该工具声明了 `x-require-confirm`），确认后真正转发到业务系统。

## 3. 关键设计

- **权限要求来自业务契约**：`x-required-permission` 由业务系统在 OpenAPI operation 上声明，平台只读不猜。平台代码里没有"取消=管理员"这类业务判断。
- **身份显式跨线程传递**：`ChatController` 在 HTTP 线程取出 `UserPrincipal`，作为参数传给线程池里的 `AgentRunner`。ThreadLocal 不跨线程池，循环内再取会拿到 null。
- **确认项绑定发起人**：`ConfirmController` 在批准/拒绝前核对 `pending.userId() == 当前 uid`。`confirmToken` 只是随机 UUID，若不核对归属，任何登录用户拿到 token 就能批准他人的敏感操作。
- **业务侧身份**：转发时附服务级凭证 `X-Service-Key` 与 `X-On-Behalf-Of-User: {uid}`；业务系统仅在服务凭证校验通过时才采信用户头。
- **闸门 2 只有二十行**：定位工具 → 查权限集合 → 不命中返回文本 → 放行给转发器。安全逻辑短，是为了能被审计和穷举测试。
- **管理端按 URI 映射权限码**：`/admin/rbac` → `admin:rbac`、`/admin/knowledge` → `admin:knowledge`、`/admin/sources` → `admin:source`、`/admin/tools` → `admin:tool`，其余 `/admin/**` → `admin:console`，不按角色写死。

## 4. 深挖问题清单

**Q：为什么闸门 1 不把没权限的工具裁掉？**
裁掉后模型看到的世界里"这个工具不存在"，它会对用户说"我没有这个功能"——把权限问题说成了能力问题。用户得不到"去找管理员开权限"这个正确结论。所以全量下发、权限要求写进描述，模型做三段式判断：提前判断 → 照常尝试 → 被拒后转述。

**Q：全量下发会不会让模型更容易被诱导去调管理员工具？**
会更容易"尝试"，但尝试不等于成功。真正的边界是闸门 2；模型幻觉或被注入后硬调，仍然会被代码拒绝。闸门 1 的作用是让模型少走弯路，不是拦住谁。

**Q：为什么鉴权不放在 prompt 或模型侧？**
prompt 是模型输入的一部分，可被注入覆盖；模型没有可信身份。鉴权必须由不经过模型的代码，用会话绑定的身份完成。

**Q：AI 幻觉出一个不存在的工具名怎么办？**
`invoke` 先按名称定位，找不到就返回 `isError` 文本（未知工具），不会执行任何东西。

**Q：拒绝为什么返回文本而不是抛异常？**
抛异常会打断 ReAct 循环，模型没有机会解释。文本观察让模型把拒绝转述给用户，决策循环继续。

**Q：确认和鉴权谁先？**
现在是**先只读预判、再确认、最后执行点鉴权**。`AgentRunner` 看到 `require_confirm` 时先调 `ToolGateway.denial` 做权限预判：权限不足直接返回闸门 2 同款拒绝文本，不弹确认；预判通过才挂起 `ConfirmManager`，用户同意后再进入闸门 2 的强制鉴权。

这个顺序是修出来的：原先直接先确认、后鉴权，无权限用户会看到确认弹窗、点完同意才被告知"权限不足"。安全上无害（鉴权始终在执行前），体验上是把权限问题拖到了两秒之后。改动守住一条原则：**前置预判只能"跳过确认"，不能"拦截执行"**——预判只为少打扰用户，真正的安全边界仍是执行点的闸门 2。

**Q：敏感操作的判定也是模型决定吗？**
不是。`x-require-confirm` 由业务系统在契约里声明；平台额外保留 `DELETE` 天然敏感这条 HTTP 语义常识。平台不按 summary 里的"取消/退订"猜。

**Q：用户 A 能不能看用户 B 的会话/预订？**
会话入口 `SessionController` 用 `ownsSession` 校验归属，他人会话 403；确认入口 `ConfirmController` 校验确认项发起人；业务数据归属由业务系统依据 `X-On-Behalf-Of-User` 过滤。平台不替业务系统做数据级权限。

**Q：确认 token 被别人拿到怎么办？**
token 是随机 UUID，且 `ConfirmController` 会核对 `pending.userId()` 与当前登录用户，不匹配返回 `completed=false`。token 一次性使用，超时或完成后即失效。剩余风险是多实例部署下挂起项不共享（见下）。

**Q：契约漏写 `x-required-permission` 会怎样？**
当前视为**全员可用**（fail-open）。对新增写接口，对账会产生 `PERMISSION_UNDECLARED` 告警，但只告警、不阻断。这是当前最需要补的授权缺口：生产环境应要求写操作必须声明，或把未声明的写接口默认导入为禁用。这也是"业务系统只声明"模式的代价——声明漏了，平台只能告警，不能替它猜。

**Q：模型被拒后会无限重试吗？**
prompt 要求"不要重试超过一次"，但代码层没有为单个工具设重试计数；真正的兜底是 `maxSteps=8`。每次重试都会再次命中闸门 2，不会越权，但会浪费步数。生产可在循环里加同工具失败计数。

**Q：多实例下确认挂起怎么处理？**
当前 `ConfirmManager` 是单实例内存实现，重启丢确认项即视为拒绝（语义安全）。多实例需要会话粘性或把挂起项入库——见决策 08 第 9 条的边界说明与本文 §6。

**Q：这二十行代码测过什么？**
`ToolAccessServiceTest` 覆盖闸门 1 全量下发、闸门 2 拒绝/放行/`*` 通配、未知工具、非法 JSON、转发失败回喂；`AgentRunnerTest` 覆盖确认三态、预判顺序与超步数；`ConfirmManagerTest` 覆盖同意/拒绝/超时；`JwtAuthFilterTest` 覆盖 401/403 与 `/admin/**` 权限映射。

## 5. 落地程度与生产差距

| 能力 | 代码与测试证据 | 完成度 |
|---|---|---|
| 闸门 1：全量下发 + 权限写描述 | `ToolAccessService.listForModel`；`ToolAccessServiceTest` | 接近生产 |
| 闸门 2：执行点鉴权、`*` 通配 | `ToolAccessService.invoke` / `permissionDenial`；`ToolAccessServiceTest` | **接近生产**（唯一安全边界） |
| 闸门 3：确认挂起、超时拒绝、归属校验 | `AgentRunner` + `ConfirmManagerImpl` + `ConfirmController`；`AgentRunnerTest` / `ConfirmManagerTest` | 单实例可用；多实例为演示级 |
| RBAC：每请求回库、降权即时生效 | `JwtAuthFilter` + `RbacService.loadPrincipal`；`JwtAuthFilterTest` / `RbacServiceImplTest` | 接近生产（单角色模型） |
| 认证基线：JWT fail-fast（`JWT_SECRET` 不足 32 字节拒绝启动）、PBKDF2-HMAC-SHA256、同用户 5 分钟 5 次失败即拒绝 | `JwtService` / `PasswordHasher` / `LoginThrottle`；对应单测 | 接近生产（单实例限流） |
| 业务身份透传 | `GenericHttpForwarder` 附加服务凭证与 `X-On-Behalf-Of-User` | 通道可用；用户 id 映射是演示级 |
| 工具调用审计与限流 | 仅 `chat_message` 轨迹、SSE 事件与日志 | 演示级 |

**结论**：核心安全边界（闸门 2）是真正落地的，单实例、单租户、小规模下可以按"接近生产"讲。不能按生产讲的部分集中在**横向扩展**（确认/限流状态在进程内）、**授权治理**（缺声明即 fail-open、无数据级权限）、**审计与配额**（无独立调用审计、无限流）。

## 6. 后续拓展：问题与解决办法

| 拓展点 | 现在的问题 | 解决办法 | 触发条件 |
|---|---|---|---|
| 多实例确认 | 挂起项在单机内存，别的实例批准不了 | 建 `pending_confirm` 表（token、uid、session、工具、参数、过期时间、状态），用 CAS 更新状态；SSE 实例与批准实例通过共享存储/消息通知 | 部署副本数 > 1 |
| 写接口默认拒绝 | 契约漏声明时写操作对全员开放 | POST/PUT/PATCH/DELETE 必须声明权限，否则导入为 `enabled=0` 或直接拒绝该 operation | 正式接入业务系统前 |
| 工具级审计与限流 | 只有聊天轨迹，无法按工具统计拒绝/调用量 | 独立 `tool_call_audit` 表 + Micrometer 计数；按用户/工具做令牌桶限流 | 合规审计或出现滥用 |
| 多角色 / 来源级角色 | 一个全局角色对所有系统生效 | 增加 `(user_id, source_key) -> role` 映射，闸门 2 按来源取并集；契约声明不变 | 同一用户在不同系统角色不同 |
| 强制下线 / token 撤销 | JWT 2 小时有效，降权要等下一次请求回库，但无法主动踢下线 | `app_user.token_version` 写进 JWT，过滤器比对版本；或维护短期 denylist | 安全合规要求即时撤销 |
| 高风险操作二次认证 | 确认只是点按钮 | 确认流程接入重新输入密码 / MFA；把 `ConfirmManager` 从"确认"扩展为"step-up" | 资金、删除等高风险操作 |
| 登录限流跨实例 | `LoginThrottle` 是单机内存 | 改用 Redis 计数或数据库窗口计数 | 部署副本数 > 1 |
