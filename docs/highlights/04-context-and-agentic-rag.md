# 亮点 ④：上下文工程——分层记忆 + Agentic RAG

> 一句话：**不是把更多内容塞进上下文，而是让模型在需要时自己取**。会话历史用"内部工具调回"，制度文档用"模型自主检索"。
>
> 代码入口：`agent/context/ContextTrimmer`、`agent/memory/HistoryRecallTool`、`knowledge/search/KnowledgeSearchService`、`knowledge/chunk/MarkdownChunker`
> 背景决策：`docs/adr/ADR-003-context-trimming.md`、`docs/adr/ADR-005-session-memory-recall.md`、`docs/KNOWLEDGE-RAG.md`

## 1. 30 秒版本

上下文只放三类东西，其余按需取回：

| 层 | 载体 | 进入上下文的方式 |
|---|---|---|
| 热：最近对话 | 最近 6 条消息 | 每轮必带 |
| 温：早期摘要 | `checkpoint` | 裁剪时压成一条 SystemMessage |
| 冷：全量历史 | `chat_message` | 模型调用内部工具 `recallHistory` 按关键词调回 |
| 外部知识 | `knowledge_chunk` + pgvector | 模型调用内部工具 `search_knowledge` 检索 |

关键区别：**工具是"全量下发、执行点拒绝"，知识是"检索时过滤"**——文档内容一旦进入上下文就收不回，所以无权内容必须从不进入候选集。

## 2. 裁剪策略

- 触发条件：字符数 / 2 粗估 token，超过阈值（默认 6000）；
- 保留：system + 最近 6 条；
- 更早内容压成一条摘要 SystemMessage，落 `checkpoint`；
- 确定性规则，不额外调用模型，单测友好。

实测（qwen-turbo，30 轮长会话）：

| 指标 | 结果 |
|---|---|
| 总 Token | 166,656 → 113,716，**降 31.8%** |
| 单次调用 prompt 末轮 | 7860 → 1684，**降 78.6%** |
| 代价 | 裁剪导致遗忘，模型重查次数 **+48.8%** |

代价是诚实的：被裁掉的是结论，模型会多查一次业务系统。这比"上下文无限增长"更可控。

## 3. 为什么会话记忆不用 RAG

| 维度 | RAG | 内部工具调回（当前） |
|---|---|---|
| 嵌入质量 | 对话短碎、指代多，单条嵌入几乎无意义 | 不嵌入，按关键词查 MySQL |
| 成本 | 每条消息写入时付嵌入费 | 缺了才查，读取时付费 |
| 失败可见性 | top-k 自动注入，失败不可见 | 模型发起、失败如实回喂、可换词重试 |
| 基础设施 | 向量库、切块、调参、评估 | 复用已有两张表 + 一个内部工具 |
| 决策权 | 系统猜你要什么 | 模型知道自己缺什么 |

RAG 适合"海量非结构化文档 + 查询模糊"；对话历史恰恰相反——短、碎、强上下文依赖。详见 `docs/MEMORY-STRATEGY.md`。

## 4. 知识库 RAG 的四层

**① 切块**
按 Markdown 标题切，因为作者写标题时就在划语义边界；约 800 字符一块；只在硬切时留 100 字符重叠（按标题切不留，避免相邻主题互相污染）；块前缀"文档 > 章节"弥补"上述标准"这类指代失效。切块版本号参与索引指纹，改规则必须加一。

**② 权限**
`visible_permission` 写在文档 front-matter，缺省 `public`；权限过滤写进 pgvector 检索 SQL 的 `filterExpression`，无权块从不进入候选集（`*` 不过滤，否则只看 `public` 与命中用户权限集合的块）。也不告诉模型"存在你看不到的文档"——用户问制度时"没有相关规定"比"有但你看不了"更合理。

**③ 索引**
四项判据决定是否重建：status（FAILED 必重试）、content hash、embedding model、切块参数版本。写入采用版本化：块 id 由 `doc_path#序号` 确定性生成，先 add 新块、再删新版本不再包含的 stale id，避免重建期检索空白。任务表的部分唯一索引做跨实例互斥。

**④ 可观测与评估**
检索写审计表（谁、查了什么、命中来源、耗时，不记正文）；Micrometer 指标；embedding 用量计入 `knowledge_usage`；固定题库跑 Recall@K / MRR / 空结果率，`POST /admin/knowledge/eval` 可复跑。

## 5. 深挖问题清单

**Q：为什么裁剪保留最近 6 条，而不是按 token 精确切？**
按条数是确定性规则，不需要 tokenizer，也不会因为一条超长消息导致整段历史被清空。6 条覆盖一个典型 ReAct 往返（用户 → 决策 → 工具 → 观察 → 回答）。代价是粗粒度，已用 31.8% 的实测收益验证值得。

**Q：摘要会不会丢关键事实？**
会，这正是代价。所以摘要只负责"温层"，关键事实可以靠 `recallHistory` 从原始消息调回——摘要不是唯一副本。

**Q：`recallHistory` 为什么不用向量检索？**
对话消息短碎、上下文依赖强，嵌入质量差；而且模型明确知道自己要找什么（"上次那个会议室"），关键词检索 + 失败可见足够。少一个向量库、少一套调参。

**Q：知识检索为什么不让模型自己决定？**
正是让模型自己决定——`search_knowledge` 是模型自主调用的工具，不是每轮自动注入。平台只提供能力，调用时机由模型判断。

**Q：检索为空怎么办？**
先向量检索，空结果时用 `raw_text ILIKE` 关键词兜底（LIKE 字符已转义）；仍为空则如实返回"未检索到相关规定"。检索失败不影响对话，只作为文本观察。

**Q：无权文档为什么不能检索后再过滤？**
内容一旦进入模型上下文就收不回，模型可能复述、摘要或据此回答。过滤必须在候选集之前完成。

**Q：索引进度与一致性怎么保证？**
版本化写入 + stale id 清理；任务表部分唯一索引防止两个实例同时重建；RUNNING 超时自动标 FAILED，避免进程被 kill 后永久阻塞。

**Q：怎么证明 RAG 有效？**
固定 12 题题库，实测 Recall@4 1.00 / MRR 0.917。此前切块 bug（导语并入首节时标题丢失）导致 Recall@4 只有 0.833 / MRR 0.792，正是评估集发现的，修复后回升。

**Q：embedding 模型换了怎么办？**
`knowledge_doc` 记录模型名，启动时与配置不一致则全量重建；不同模型的向量空间不可比，不能增量混用。

**Q：知识库没配 key 会怎样？**
整个 `knowledge/` 包不装配，`search_knowledge` 不注册，其余功能不受影响。配了 key 但 Postgres 不可达则 fail fast——不能静默摘掉，否则用户会把"查不到"误判成检索质量问题。

## 6. 已知边界

- 跨会话记忆为零（偏好、约束不跨会话保存）；
- 对话历史的冷层按关键词召回，不做语义召回；
- 知识库只有一份小规模语料，Evaluation 题库也只有 12 题；
- 没有上下文压缩质量的人工评估，只有 token 与重查次数指标；
- 多语料/多租户隔离未实现。
