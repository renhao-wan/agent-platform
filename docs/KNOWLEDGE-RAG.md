# 知识库 RAG 设计：切块、检索与 Agent 自主调用

> 本文是知识库子系统（内部工具 `search_knowledge`）的设计基线，记录**每一环的候选方案、
> 选定理由与被放弃的代价**。结论先给：RAG 做成 Agentic 形态，语料来自平台本地目录，
> 向量库用 PostgreSQL + pgvector，切块按 Markdown 标题。
>
> 与 `MEMORY-STRATEGY.md` 的关系：那份文档论证的是"**会话记忆**不该用 RAG"，本文论证的是
> "**知识文档**该用 RAG"。两者不矛盾，原因见 §2——语料性质不同，结论自然不同。
>
> 状态：设计已定稿，待实现。

---

## 1. 定位与边界

**一句话**：平台管"怎么找到"，业务系统与运维管"写了什么"。

| 归属 | 内容 |
|---|---|
| 平台负责 | 目录扫描、切块、向量化、建索引、相似度检索、角色过滤、结果注入、增量更新 |
| 平台不负责 | 制度写什么、谁维护文档、文档里的业务语义（例如"差旅上限为什么是 3000"） |

这条边界和"平台不编码业务语义"是同一条原则的延伸：删掉任何一份知识文档，平台代码不需要改。
文档内容变更只触发重新索引，不触发任何代码变更。

**形态是 Agentic RAG，不是 naive RAG**：

- naive RAG：每轮对话前强制检索 top-k，把结果塞进 system/user 消息。
- 本方案：检索封装为**平台内部工具** `search_knowledge`，由模型在 ReAct 循环里自主决定何时调用、
  用什么 query、要不要追问后再查。

选择依据只有一条：**这个决策是否只有模型能做出**。多轮对话中，"那超过部分呢"这类追问本身
不含可检索信息，query 必须由模型结合上文构造；用户问"帮我订会议室"时检索制度文档是纯噪音。
naive RAG 把"要不要查、查什么"从模型手里拿走，等价于让一个看不见对话的组件猜意图。

`search_knowledge` 与 `recallHistory` 同类：模型需要它，且**没有任何业务系统能提供它**。
因此不进工具层、不过闸门 2、不参与工具路由，始终在册。

## 2. 为什么这次 RAG 是对的（与 ADR-005 的边界对照）

ADR-005 拒绝的是**把对话记忆做成 RAG**，不是拒绝 RAG 本身。两类语料的性质对照：

| 维度 | 会话消息（ADR-005 拒绝） | 知识文档（本文采纳） |
|---|---|---|
| 单条长度 | 短、碎（"就订那个"） | 长、自包含（一节讲完一条规则） |
| 上下文依赖 | 强，指代必须结合前文 | 弱，正文自带主语与条件 |
| 结构 | 无 | 作者写的标题层级就是语义边界 |
| 写入成本 | 每条消息都付费，且多数永不回读 | 每份文档付一次，长期复用 |
| 查询来源 | 模型猜"缺什么" | 用户主动问制度/流程，意图明确 |
| 失败可见性 | 无需 | 工具调用有 `tool_call` / `tool_result` 事件，可观测 |

对话消息的嵌入质量天然差，且为 90% 不会再被引用的内容预付嵌入成本；知识文档恰恰相反——
内容自包含、结构清晰、会被反复检索。**同一个技术在不同语料上收益完全不同**，这是两份文档
结论相反的全部原因。

## 3. 链路全景

```
knowledge/*.md
   │  ① 扫描（启动时，毫秒级）
   ▼
content hash 比对 ──未变──▶ 跳过（零 embedding 调用）
   │ 变更/新增
   ▼
② 按标题切块 + 前缀增强
   ▼
③ bge-m3 向量化（1024 维，SiliconFlow）
   ▼
④ 写入 pgvector（vector_store + knowledge_doc）

用户在对话中提问
   ▼
模型决定调用 search_knowledge(query, topK)
   ▼
⑤ 向量化 query → SQL 相似度检索（WHERE 角色过滤 + ORDER BY 距离 LIMIT k）
   ▼
⑥ 拼装条文（带来源标题）→ ToolResponseMessage → 下一轮生成
```

关键约束：**①～④ 全部不在请求路径上**。启动路径上零 embedding 调用，对话时只发生一次
query embedding + 一次 SQL 查询。

## 4. 切块策略（核心权衡）

### 4.1 候选方案

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| 固定长度 | 每 N 字符切一刀 | 实现最简单 | 把一条完整规则拦腰截断："单次上限 3000 元"与"超过部分需部门审批"分属两块，单独召回任一块都答错 |
| 递归字符 | 按 `\n\n` → `\n` → `。` 逐级降级切 | 比固定长度好，能保住段落 | 切点仍与语义无关；无法生成有意义的前缀 |
| 按结构切 | 以 Markdown 标题为边界 | 切点由作者确定，可解释 | 依赖文档结构规范 |
| 语义切分 | 用相邻句向量相似度找断点 | 理论上最贴合语义 | 索引阶段成本翻倍；改一句话可能导致整篇重切；对已有标题的文档收益不抵成本 |

**选定：按结构切。** 知识文档是人工整理的，作者写标题时就在划定语义边界——这是免费的、
比任何算法都准的先验。语义切分适合混乱语料（聊天记录、爬虫页面），不适合规范 Markdown。

### 4.2 具体规则

1. **H1 是文档标题**（缺失时取 front-matter `title`，再缺失取文件名），不进块正文，只做前缀。
2. **H2 是主切分点**：每个 H2 及其下属内容成一块。
3. **块过大（> 800 字符）**：按空行拆段落继续切；仍过大则按句号切；仍过大才硬切 800 字符，
   此时相邻片段保留 **100 字符重叠**，防止句子被截断。
4. **块过小（< 50 字符）**：与下一节合并；若已是最后一节，与上一节合并。
5. **H3 不切分**，除非其所属 H2 块超长——此时 H3 作为次级切分点。
6. **每个块前缀 `文档标题 > 章节标题`**，例如 `差旅报销制度 > 交通与住宿标准`。

### 4.3 三个参数的理由

**块上限 800 字符。** 这里权衡的是两个方向：

- 太小（200～300）：一条规则的条件与结论被拆开，召回"上限 3000 元"却丢失"超过部分需部门审批"，
  模型会给出错误结论。**知识文档的失败模式是"答得理直气壮但漏了例外条款"，比检索不到更危险。**
- 太大（2000+）：块内主题混杂，向量被多个主题平均，相似度被稀释；同时单块占用上下文预算过多，
  top-k 稍大就挤掉对话历史。

800 字符下，一节通常 2～4 个自然段，正好是一条完整规则加它的适用条件，约 400～600 token。
这个数字应结合真实语料校准——文档里的制度条目如果普遍更长，调这个参数，而不是改切分算法。

**最小块 50 字符。** 独立成块的小节（"本制度自 2026 年 1 月 1 日起施行"）单独召回时几乎没有
检索价值，反而占用 top-k 名额。合并后至少能附着在一条有内容的规则上。

**重叠 100 字符只用于硬切。** 按标题切分时**不需要重叠**——标题就是语义边界，相邻块本就
主题不同。给它们加重叠只会让两块内容互相污染，增加 embedding 成本。重叠的唯一合理场景是
"同一句话被字符数硬生生切开"，所以只在第 3 条的最后一步使用。

### 4.4 前缀增强：弥补切块的先天缺陷

切片脱离原文后，指代会失效。实例：

```
原文：## 住宿标准
      一线城市每晚不超过 600 元，二线城市不超过 400 元。
      ## 超支处理
      超过上述标准的，需提前获得部门负责人书面同意。
```

`超过上述标准的` 单独成块时，"上述标准"指向不明。加上前缀后：

```
[差旅报销制度 > 超支处理]
超过上述标准的，需提前获得部门负责人书面同意。
```

前缀同时参与向量化与最终返回，既改善召回（"差旅 住宿 超支"进入块向量），也让模型能读懂
指代关系。代价是所有块多出十几个 token——这是全篇唯一"钞能力能直接买到检索质量"的地方。

### 4.5 特殊内容

- **表格整表不切**。表格的语义在行列关系里，拆开即失效。超长表格按行切，但**每片重复表头**。
- **代码块 / 引用块不切**，视为不可分割单元，随所属小节走。
- **front-matter 不参与向量化**（`---` 头部），只读取 `visible_role` 元数据（见 §8）。

### 4.6 为什么不做父子块（small-to-big）

父子块是"用小块检索、用大块返回"的常见优化：小块向量更聚焦，命中后扩大上下文再喂模型。
本方案不做，理由：

1. 我们的块本来就不大（≤ 800 字符），检索粒度与返回粒度一致，没有"命中了但上下文不够"的问题；
2. 父子块要额外存两份内容并做二次查询，复杂度换来的收益需要真实 bad case 证明；
3. 切块规则本身已用前缀弥补了指代问题，父子块要解决的核心痛点在这里不存在。

**这是规模化后的优化项，不是起点。** 如果将来出现"命中正确小节但模型仍答错"的样本，
第一反应应该是调块大小与前缀，而不是直接上父子块。

## 5. Embedding

| 项 | 选择 | 理由 |
|---|---|---|
| 模型 | `BAAI/bge-m3`（SiliconFlow 托管） | 中文检索效果稳定、1024 维、免费额度足够本项目语料规模；DeepSeek 无 embeddings 接口 |
| 维度 | 1024 | 与 `vector(1024)` 表结构绑定，**一经确定不可静默更换**——换模型必须重建索引 |
| 距离 | cosine | 文本嵌入的常规选择；bge 系列输出已归一化，cosine 与内积排序等价 |
| 调用时机 | 仅索引变更块 + 每次查询一次 | 不在对话路径上批量调用 |

**更换 embedding 模型是有代价的操作**：维度变化要重建表；维度相同但向量空间不同，旧向量与
新 query 不可比。因此 `knowledge_doc` 记录 `embedding_model`，启动时若与配置不一致则整库重建
并打 WARN 日志。这条比"记得手工重跑"可靠。

**Spring AI 接入的坑**：OpenAI 自动配置只认一个 `base-url`，chat 已被 DeepSeek 占用，
embedding 必须单独构造 `OpenAiEmbeddingModel` bean 指向 SiliconFlow，不能靠 `application.yml` 一把梭。

## 6. 存储：为什么是 pgvector

| 候选 | 优点 | 不选的理由 |
|---|---|---|
| MySQL JSON 列 + 内存余弦 | 不新增组件 | 全量加载后计算，角色过滤只能在算完之后做；无索引；规模上百块即开始难堪。本质是自己写半个向量库 |
| Qdrant / Milvus | 专业、性能强 | 多一个需要运维的组件；本项目数据量远未到需要它的程度；且元数据过滤要另学一套语法 |
| **PostgreSQL + pgvector** | 一个容器；相似度与元数据过滤在同一条 SQL；HNSW 成熟 | 需要额外一个 DataSource |

选择的关键不是性能，是**过滤与检索能合并成一次查询**：

```sql
SELECT content, metadata
FROM vector_store
WHERE metadata->>'visible_role' IN ('PUBLIC', 'ADMIN')   -- 权限过滤
ORDER BY embedding <=> :queryVector                       -- 相似度排序
LIMIT 4;                                                  -- top-k
```

这直接落实了 §8 的权限原则——**无权内容从不进入候选集**，而不是"查出来再扔掉"。

**索引与参数**：HNSW（建索引慢、查询快、无需预训练），`m = 16`、`ef_construction = 64`，
查询时 `hnsw.ef_search = 40`。这是 pgvector 的常规起点，语料规模下无需调优；被问到时能说出
"m 与 ef_construction 是建索引时的召回率/构建时间权衡，ef_search 是查询时的召回率/延迟权衡"即可。

**部署**：`pgvector/pgvector:pg16` 容器，端口 5433，独立于 MySQL（3307）。
**业务数据在 MySQL，知识向量在 Postgres**——两类数据生命周期与访问模式不同，不强行合并。

## 7. 检索策略

### 7.1 参数

| 参数 | 默认 | 权衡 |
|---|---|---|
| `topK` | 4 | 每块约 500 token，4 块约 2000 token。给少了容易漏掉后半段规则，给多了稀释上下文并引入噪音。模型可二次检索补查，所以默认偏保守而非偏多 |
| `topK` 上限 | 8 | 防止模型一次拉满挤占上下文；同时兜住模型传错参数 |
| 相似度阈值 | 0.30（**待真实语料校准**） | 低于阈值的块直接丢弃。宁可返回"未检索到"，也不塞入弱相关内容——弱相关内容最危险，它看起来像依据，会诱导模型编造 |

阈值必须实测校准：bge-m3 的相似度分布依赖语料与 query 风格，0.30 只是起点。校准方法：
准备 20 条"问题 → 应命中文档"的样本，看正样本最低分与负样本最高分的分界。

### 7.2 结果组织

- 按相似度降序拼接，每块前标注来源：`[来源：差旅报销制度 > 交通与住宿标准]`。
- **保留来源是硬要求**：模型回答时可以说"依据《差旅报销制度》第 X 节"，用户能自行核对；
  同时让"检索错了"这件事可被用户发现。
- 单块返回完整正文，不做二次摘要——摘要在检索层做等于用一次额外的 LLM 调用换不确定信息。
- 总返回长度设硬上限（约 8KB），与业务工具的响应截断口径一致。

### 7.3 不做重排（rerank）

rerank 用交叉编码器对 top-k 结果重新打分，通常能提升 5～15% 的精度。不做，理由：

1. 需要额外的模型调用与延迟（索引 4 片 × 一次推理），在 `topK = 4` 时收益方差不大；
2. 没有评估集就无法证明它有效——"加了 rerank 感觉更准"不是工程结论；
3. 先用阈值 + 前缀 + 标题切分把基线做好，把 rerank 留作有 bad case 时的第一步增强。

### 7.4 不做混合检索（BM25）

混合检索解决"精确术语/编号查不到"的问题（向量对专有名词不敏感）。不做，理由：

1. 中文 BM25 在 Postgres 里需要额外分词扩展（`zhparser` / `pg_jieba`），运维成本不低；
2. 当前语料是制度文档，查询以自然语言描述为主，不是产品编号检索；
3. 真的出现该 bad case（例如"报销制度里提到的 ZX-2024-07 附件"），**第一步是加 `ILIKE` 关键词兜底，
   不是上 Elasticsearch**——两行 SQL 能解决的事不要引入一个搜索引擎。

### 7.5 检索可观测性

每次检索记录到日志：`query`、命中块的 `doc_path` / `section` / 分数、耗时。
不做完整评估平台，但保留这份日志——出现 bad case 时可以复现"当时检索到了什么"，
这才有可能做校准。**面试里"你怎么知道检索效果好不好"的诚实答案是：目前靠人工样本 + 检索日志，
没到需要 RAGAS 之类自动评估的规模，但我留了数据。**

## 8. 权限：过滤在检索时，不是返回后

知识文档的权限模型与工具**方向相反**：

| | 工具 | 知识文档 |
|---|---|---|
| 拦截时机 | 执行点（事后） | 检索时（源头） |
| 原因 | 工具调用前无法预知会读到什么，执行点校验即可 | 内容一旦进入上下文就收不回来，事后过滤无意义 |
| 存在性 | 工具清单全量下发，让模型知道"有能力但无权限" | **不披露**：无权文档不出现在结果里，也不告诉模型"存在你看不到的文档" |

实现：

1. 文档 front-matter 声明 `visible_role: ADMIN`，缺省为 `PUBLIC`；切块时写入每个块的 metadata。
2. 检索 SQL 的 `WHERE` 按当前用户角色过滤（§6 示例），**无权块不参与相似度计算**。
3. 为什么缺省是 `PUBLIC` 而不是"缺省拒绝"：知识库的默认场景是全员可见的制度文档；
   缺省拒绝会让每份文档都必须显式声明，违反"加一份文档只写内容"的简洁目标。
   **这是有意的选择，不是疏漏**——敏感文档必须显式标注，这一点写进文档模板说明。
4. 索引管理与重建接口 `POST /admin/knowledge/reindex` 走现有 `/admin/**` 的 ADMIN 校验。

注意与闸门 1 的区别：工具**全量下发**是为了让模型能把权限问题讲成权限问题；知识文档**不披露**
是因为没有对应的"转述"需求——用户问制度时，返回"没有相关规定"比"有相关规定但你看不了"
更符合直觉，也避免泄露敏感文档的存在。

## 9. 增量索引与更新

### 9.1 数据表（Postgres）

```sql
CREATE TABLE knowledge_doc (
    doc_path        VARCHAR(255) PRIMARY KEY,   -- 相对 knowledge/ 的路径
    content_hash    CHAR(64) NOT NULL,          -- SHA-256
    chunk_count     INT NOT NULL,
    embedding_model VARCHAR(64) NOT NULL,       -- 换模型即需重建
    indexed_at      TIMESTAMP NOT NULL,
    status          VARCHAR(16) NOT NULL        -- INDEXED / FAILED / STALE
);
```

向量本体由 Spring AI 的 `vector_store` 表承载，`metadata` 中存 `doc_path`、`section`、
`visible_role`、`chunk_index`。

### 9.2 流程

- **启动**：扫描 `knowledge/**/*.md` → 计算 hash → 与 `knowledge_doc` 比对。**只对变更/新增文档
  切块与 embedding**，未变文档零调用。文件消失则按 `doc_path` 删除对应向量与记录。
- **异步**：索引跑在独立线程池（`knowledge-index-*`），不阻塞 Web 启动。启动日志报出
  "本次索引 N 份 / 跳过 M 份"。
- **手动全量重建**：`POST /admin/knowledge/reindex`；换 embedding 模型时也会自动触发。
- **一致性**：先删旧块再写新块。向量表与 `knowledge_doc` / `knowledge_chunk` 分属两套存储，
  不做跨库事务：写向量失败时该文档标 `FAILED`，不写入记录，下次扫描或手动 reindex 会重试。
  "删了一半"的最坏结果是该文档暂时检索不到，而不是新旧内容混杂。

### 9.3 为什么启动时全量扫描但不全量向量化

用户此前的质疑是"一次启动拉上千个文件吗"。答案是：

- **扫描**上千个文件是毫秒级 IO，且只读文件头与正文算 hash，没有网络调用；
- **向量化**只发生在变更文档上。首次部署约一次成本（N 份文档），之后每次启动通常为 0；
- 即便单份文档索引失败，也只影响该文档（`status = FAILED`），其余照常可用。

## 10. 工具契约

```json
{
  "name": "search_knowledge",
  "description": "检索公司制度、流程与规范文档（报销制度、差旅标准、会议室使用规定、报修流程等）。当用户询问规定、标准、额度、时限、流程步骤等制度类问题时使用。注意：查询用户的业务数据（报销单、订单、工单）请使用业务系统工具，不要用本工具。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "检索问题，写清主题与条件，例如「差旅住宿费上限」" },
      "topK":  { "type": "integer", "description": "返回条数，默认 4，最大 8" }
    },
    "required": ["query"]
  }
}
```

描述里明确划出"制度文档 vs 业务数据"的边界——这是防止模型拿知识库回答业务数据问题
（或反之）的第一道也是唯一一道防线，必须写成动作句与反例。

**返回格式**：

```
[来源：差旅报销制度 > 交通与住宿标准]（相关度 0.82）
一线城市每晚不超过 600 元……

[来源：差旅报销制度 > 超支处理]（相关度 0.74）
超过上述标准的，需提前获得部门负责人书面同意。
```

**失败语义**（与平台既有契约一致，永不抛异常）：

| 情况 | 返回 |
|---|---|
| 未检索到（全部低于阈值） | `未在知识库中检索到与「xxx」相关的内容，可尝试更换关键词。` |
| 未配置 embedding key | 工具不注册（见 §11），模型看不到它 |
| embedding 服务异常 | `知识库检索暂不可用，请稍后再试。` |
| 参数非法 | `search_knowledge 参数无效：请传 {"query":"具体问题"}，query 必填且不能为空。` |

## 11. 优雅降级

`EMBEDDING_API_KEY` 未配置时：

- 不创建 embedding bean、不构造 `PgVectorStore`、不注册 `search_knowledge`；
- 不连接 Postgres、不建表；
- 打一条 INFO：`知识库未启用（EMBEDDING_API_KEY 为空）`。

**平台其余功能完全不受影响，`mvn test` 也不依赖 Postgres**（检索逻辑用 mock / `SimpleVectorStore` 测）。
这保持了"克隆即可跑通"的现有调性：新增能力是可选增强，不是启动前置条件。

## 12. 明确不做（与被否原因）

| 不做 | 原因 |
|---|---|
| naive RAG（每轮自动检索） | 决策权应从模型手里拿走吗？见 §1 |
| 语义切分 | 结构化文档已有免费且更准的切点，见 §4.1 |
| 父子块 small-to-big | 当前块大小下痛点不存在，见 §4.6 |
| 固定 overlap | 按标题切分无重叠需求，会污染相邻块，见 §4.3 |
| rerank | 无评估集证明收益，留作有 bad case 时的第一步，见 §7.3 |
| BM25 混合检索 | 中文分词扩展成本高，先 `ILIKE` 兜底，见 §7.4 |
| 向量数据库集群（Milvus 等） | 数据量不匹配，见 §6 |
| 接飞书/语雀等外部来源 | 本地目录先跑通；来源是适配器问题，不是检索架构问题 |
| 文档热更新监听 | 改完调一次 reindex；文件监听在容器与编辑器下行为不一，不值 |
| 自动评估（RAGAS） | 规模未到；先留检索日志，见 §7.5 |

## 13. 常考追问与回答要点

| 追问 | 回答核心 |
|---|---|
| 为什么按标题切，不按固定长度？ | 作者写的标题就是语义边界，比算法猜准且零成本；固定长度会把一条规则的结论与例外拆开，这是知识库最危险的错误类型 |
| 块大小怎么定的？ | 800 字符 ≈ 一条完整规则加适用条件；太小丢例外条款，太大稀释向量并挤占上下文。这是起点，要按真实语料校准 |
| 为什么不做 overlap？ | 按标题切分时相邻块本就主题不同，重叠会互相污染；只在硬切超长节时用 100 字符重叠防止断句 |
| 为什么要加"文档 > 章节"前缀？ | 切片脱落后"上述标准"这类指代失效；前缀既改善召回又让模型能读懂指代，是全篇性价比最高的增强 |
| top-k 怎么选？ | 4 是上下文预算与召回率的平衡点；模型可二次检索补查，所以宁可少而准；上限 8 防挤占上下文 |
| 怎么知道检索效果？ | 目前靠 20 条人工样本校准阈值 + 检索日志（query/命中/分数），未到需要自动评估集的规模，但数据留了 |
| 为什么不用 rerank？ | 需要额外模型调用，且没有评估集证明有效；先做好切块与阈值基线，rerank 留作有 bad case 时第一步 |
| 为什么不做混合检索？ | 中文 BM25 要装分词扩展；当前查询以自然语言为主，真出精确术语问题先加 ILIKE 兜底 |
| 为什么用 pgvector 不用 Chroma/Qdrant？ | 角色过滤与相似度能合并成一条 SQL，无权内容不进候选集；少一个要运维的组件；亿级再谈 Milvus |
| 文档更新怎么办？ | 启动时算 hash 比对，只重索引变更文档；删文件即删向量；也可调 `/admin/knowledge/reindex` |
| 启动会不会拉上千文件？ | 扫描是毫秒级本地 IO，向量化只作用于变更文档；首次部署一次成本，之后通常为 0 |
| 权限怎么控？ | 过滤在检索 SQL 内，无权块从不进入候选集；且不向模型披露无权文档的存在 |
| 为什么不做成 naive RAG？ | 要不要查、查什么只有模型知道——多轮追问的 query 必须结合上文构造；检索失败也要模型可见可重试 |
| 检索错了模型会怎样？ | 返回带来源，用户可核对；模型可换关键词重查；阈值丢弃弱相关结果，宁可说"没找到"也不给错误依据 |
| 换了 embedding 模型怎么办？ | 维度或向量空间变了必须全量重建；`knowledge_doc` 记录模型名，启动时不一致自动重建并告警 |

## 14. 落地顺序与验收

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | compose 加 pgvector；独立 DataSource + `PgVectorStore` bean | 能写入一条向量并按相似度查回 |
| 2 | 切块器（纯函数） | 单测覆盖：标题切分 / 超长硬切与重叠 / 过小合并 / 前缀 / 表格与代码块 |
| 3 | embedding 客户端 + 目录扫描 + hash 增量 | 二次启动零 embedding 调用；改一份只重算一份 |
| 4 | `search_knowledge` + 接入 `AgentRunner` 两个位置 | 单测；模型能自主调用并引用来源 |
| 5 | 四份语料（报销制度 / 差旅标准 / 会议室规定 / 报修流程） | 内容与 stub 数据可对撞 |
| 6 | 端到端 | 问"差旅住宿上限是多少" → 检索；问"我这月报销超标了吗" → 检索 + 查单据协同 |

**语料设计原则**：制度里的数字要与 stub 业务数据能对撞（例如制度写"差旅单次上限 3000 元"，
而 `admin` 的报销单 601 是 4200 元），才能演示"先查制度、再查单据"的两个工具协同——
这比"问一个文档里有答案的问题"高一个档次，也是 RAG 与业务平台真正咬合的证据。
