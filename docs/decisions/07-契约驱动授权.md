# 决策 07：权限要求与工具来源一律从业务契约读取，平台不编码业务语义

日期：2026-10-19　状态：已采纳

## 背景

M5 之后平台的接入面已经收敛为"一份 OpenAPI 文档"，但权限这件事仍留了两处平台侧的人工痕迹：

1. **谁需要管理员**由 `data.sql` 里的种子语句写死——`UPDATE tool_definition SET required_role='ADMIN' WHERE name='cancel'`。这意味着平台代码库里出现了业务概念（"取消会议室预订要管理员"），每接入一个新系统、每改一次业务规则，都要回到平台改 SQL。
2. **哪些操作属于敏感**由导入逻辑按 HTTP 方法猜：POST 写 / DELETE 一律标 `require_confirm=true`。猜测的依据是 HTTP 方法的字面含义，而不是业务方对"这一步是否不可逆"的判断——查一次不落库的 POST 会被误标，而业务方认为需要确认的 PUT 却不会。

同时，工具清单的**获取方式**也是人肉的：装好平台后要人工 `POST /admin/protocols/import` 提交各个系统的契约文档。

三件事的共同点是：**平台在替业务系统保管业务知识**。这与"平台领域中立"这条不变量冲突——CLAUDE.md 里明确写着业务关键词不得出现在平台代码或 yml 里。

## 备选方案

| 方案 | 评估 |
|---|---|
| 维持现状（种子 SQL 写角色 + 按方法猜敏感度 + 人工导入） | 平台持续持有业务知识；接入方每加一个系统都要改平台侧数据，与"零改造接入"的说法自相矛盾 |
| 平台管理界面上让管理员逐个工具勾选角色与敏感度 | 把人工痕迹从 SQL 搬到 UI，业务知识仍在平台侧（且是重复维护）；两个真相来源迟早不一致 |
| **角色与敏感度由业务系统在契约里声明；工具来源在启动时自动拉取** | ✅ 采纳：平台只读契约，业务知识归业务方；接入从"三步走"变为"契约可访问即接入" |

## 决策

1. **权限要求由业务系统在 OpenAPI operation 上声明**：扩展字段 `x-required-permission`（需要什么权限）与 `x-require-confirm`（是否要人工确认）。平台导入时读进 `tool_definition`，删掉 `data.sql` 里那两条写死角色/敏感度的种子语句。
   - 兼容两种形状：手写 JSON 里的裸值（stub 用），与 springdoc `@Extension(name="x-required-permission", properties=@ExtensionProperty(name="value", value="booking:cancel"))` 生成的嵌套对象（booking 用）。
   - **业务系统只声明、不校验**。校验始终是平台闸门 2 的职责——业务系统对 AI 零感知这条不变量不变。
   - `DELETE` 天然算敏感这条保留（HTTP 方法层面的常识，不是业务知识）；其余一律以 `x-require-confirm` 为准，平台不再按方法猜。
   - **更新（决策 10）**：字段已升级为 `x-required-permission`（权限码，如 `booking:cancel`）；`x-required-role` 已彻底移除，不再保留兼容归一。"由业务契约声明"这一原则不变。
2. **闸门 1 语义从"按角色过滤"改为"全量下发 + 描述披露"**：`ToolAccessService.listVisible(gatewayId, userRole)` 被 `listForModel(gatewayId)` 取代，下发该网关全部启用工具，把角色要求写进工具描述随清单一起来。
   - 理由：按角色裁掉的话，模型看到的世界里"这个工具不存在"，于是它对用户的回答是"我没有这个功能"——**把权限问题说成了能力问题**，用户得不到"你需要找管理员开权限"这个正确结论。
   - 全量下发后模型能做三段式抉择：**提前判断**（描述里已披露角色要求）→ **尝试**（照常发起调用）→ **被拒后转述**（闸门 2 返回的 `权限不足：需要 X 角色`）。
   - **闸门 1 从此明确为体验优化，不是安全边界**；安全边界仍然只有闸门 2，其判断逻辑与文案逐字未动。
3. **工具来源在启动时自动拉取注册**：`platform.gateway.sources` 列出各业务系统的契约地址，`OpenApiSourceRegistrar` 逐个拉取、解析、注册；契约 URL 的 origin 直接作为该来源工具的调用基地址，所以契约本身不必写死主机名。
   - 单个来源失败只告警跳过，不阻断启动（一个后端没起来，不该让平台整个起不来）。
   - `sources` 清空则退回人工导入通道（`POST /admin/protocols/import` 保留）。
   - 后续（2026-10-20）：来源清单已迁入数据库注册表（决策 09），人工导入通道随之删除——它会产生没有来源归属、不参与对账的幽灵工具。
4. **用户身份透传**：转发时在服务级凭证（`X-Service-Key`）之外带上 `X-On-Behalf-Of-User: {uid}`，业务系统据此把数据记在最终用户名下——同一句话，`staff01` 与 `admin` 拿到各自的记录。业务系统仅在服务凭证校验通过时才采信该头。

## 后果

**正面**

- 平台代码与配置里不再出现任何业务关键字（"cancel""ADMIN"），"领域中立"不变量真正成立；
- 接入方加一个系统、改一次权限规则，全在自己的仓库里完成，平台侧零改动——"零改造接入"从口号变成事实；
- 权限链路成为一条可指认的证据链：**业务声明（契约扩展字段）→ 平台读取（导入解析）→ 披露（工具描述）→ 拒绝（闸门 2）→ 转述（模型回答）**，每一环都有测试或实测对应；
- stub 系统也能演示"部分接口能访问、部分不能"，闸门 2 的现场证据不再依赖 booking 一个系统。

**负面 / 代价**

- 业务方必须记得在自己的注解上声明权限，忘声明不会报错——**只会静默地不再鉴权**，这是最难发现的一类回归。对账期现在会把它暴露出来：已有声明被撤销记 `PERMISSION_REMOVED`，新增的写操作缺声明记 `PERMISSION_UNDECLARED`，都只告警不阻断。此外用 `OpenApiContractTest` 断言 booking 契约的声明形状（cancel 带两个扩展、create 不带）；
- 启动自动注册让"平台起不来"与"业务系统没起"耦合了半度：契约拉不到时工具清单会缺项。用"只告警不阻断"缓解，但排查时需要知道去看启动日志的注册结果；
- 删掉 `listVisible` 后，旧的按角色分桶缓存（`DynamicToolRegistryImpl` 曾按角色分桶）失去意义，简化为单一缓存桶——清单对所有角色一样，5 分钟刷新一次。
